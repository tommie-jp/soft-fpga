# 20. Debug Panel & Logic Analyzer: How to Use <a class="qr-link" href="../../../docs/09-PDP11/img/20-en-QR.png">QR</a>

The RTL simulator includes built-in debug features for observing the CPU's internal state in real time.
This document explains the **GPR panel**, **MMU panel**, **Logic Analyzer**,
and **PC Trigger** functions.

---

## 1. GPR Panel (General-Purpose Register Display)

The "Registers" pane displayed on the right side of the terminal.

```text
Registers
R0  003710     R1  013220
R2  000000     R3  000377
R4  001234     R5  017532
SP  177600
PC  004014
PSW KK P6 T.NZVC
```

### 1.1 Register Fields

| Field | Description |
|-------|-------------|
| `R0`–`R5` | General-purpose registers (16-bit, octal display) |
| `SP` | Stack pointer (R6) |
| `PC` | Program counter (R7) |
| `PSW` | Processor status word (described below) |

### 1.2 PSW Display Format

PSW is displayed in the format `CM PM P# T NZVC`.

```text
KK P6 T.NZVC
^^  ^  ^^^^^
||  |  |||||── C: Carry
||  |  ||||─── V: Overflow
||  |  |||──── Z: Zero
||  |  ||───── N: Negative
||  |  |────── T: Trace (trap after one instruction)
||  └───────── P#: Interrupt priority level (0–7)
|└──────────── PM: Previous mode (K=Kernel, S=Super, U=User)
└───────────── CM: Current mode
```

Uppercase letter = flag ON, `.` = flag OFF.

### 1.3 Register Value Colors

| Color | Meaning |
|-------|---------|
| Cyan | Normal (Kernel mode) |
| Blue | User mode (CM=User) |
| Orange | Snapshot immediately after a trap |
| Yellow | Field whose value changed since the last update |

## 2. MMU Panel

The "MMU" area below the GPR panel (expand/collapse with the "MMU" button).

Displays PAR (Page Address Register) and PDR (Page Descriptor Register)
split into Kernel I-space (8 pages) and User I-space (8 pages).

```text
MMU
Kernel I-space             User I-space
#  PAR        PDR    PA    #  PAR        PDR    PA
0  000000o  077406  000000  0  020000o  077406  020000
1  000200o  077406  020000  1  023400o  077406  034000
...                         ...
7  017600o  077406  176000  7  —
```

### 2.1 Column Meanings

| Column | Description |
|--------|-------------|
| `#` | Page number (0–7) |
| `PAR` | Page Address Register (upper 12 bits of physical address, octal) |
| `PDR` | Page Descriptor Register (access rights, page length, D/W bits) |
| `PA` | Actual physical base address (PAR × 64 bytes, octal) |

### 2.2 Key PDR Bits

| Bit | Name | Meaning |
|-----|------|---------|
| [3:1] | PLF | Page Length Field (number of valid sections) |
| [2] | ED | Expansion direction (0=upward / 1=downward) |
| [1] | W | Written bit (1=a write has occurred to this page) |
| [0] | D | Page access permission (0=none / 1=read-only / 2=read-write) |

The value `077406` is a typical value meaning "full length, read-write."

### 2.3 Observation Tips

- Immediately after Unix V6 boots, the Kernel I-space PARs are set and
  User I-space is all zero (no user process has started yet).
- Just before `login:` appears, the User I-space PARs change (init → getty fork).
- While a user command is running, CM=User and the User I-space mapping becomes active.

## 3. Logic Analyzer (Signal Waveform Display)

The waveform display area at the bottom of the page.
Renders the most recent 4096 clocks of signals recorded in the ring buffer.

### 3.1 Decode Lane (Bus Cycle Display)

The **Cycle decode lane** at the top of the waveform shows the type of each bus cycle as a color band.

| Color | Bus Cycle Type | Meaning |
|-------|---------------|---------|
| Blue | FETCH | Instruction fetch (read where VA == PC) |
| Green | MEM\_RD | Memory read (normal RAM) |
| Red | MEM\_WR | Memory write |
| Light green | IO\_RD | I/O page read (physical 0o760000–) |
| Orange | IO\_WR | I/O page write |
| Orange | TRAP | Trap occurred |

### 3.2 Signal List

Signals can be individually toggled ON/OFF with toggle buttons.

#### Bus Address / Data

| Signal ID | Label | Default | Description |
|-----------|-------|---------|-------------|
| `addr_p` | PhysAddr | ON | Unibus physical address (18-bit, hex) |
| `addr_v` | VA | off | Virtual address (before MMU translation, 16-bit) |
| `data` | Data | ON | Bus data (read or write value) |

#### Bus Control

| Signal ID | Label | Default | Description |
|-----------|-------|---------|-------------|
| `bus_wr` | WR | ON | Bus write strobe |
| `bus_rd` | RD | ON | Bus read strobe |
| `byte_op` | BYTE | off | Byte operation flag (MOVB/CMPB, etc.) |

#### CPU State

| Signal ID | Label | Default | Description |
|-----------|-------|---------|-------------|
| `pc` | PC | ON | Program counter (octal display) |
| `psw` | PSW | off | Processor status word (`KK P6 TNZVC` format) |
| `cm` | Mode | ON | CPU current mode (Kernel / User) |
| `pri` | Pri | off | Interrupt priority level (PSW[7:5]) |

#### Trap / Halt

| Signal ID | Label | Default | Description |
|-----------|-------|---------|-------------|
| `trapped` | TRAP | ON | Trap occurred flag |
| `halted` | HALT | ON | CPU halt flag (HALT instruction) |

#### Interrupts

| Signal ID | Label | Default | Description |
|-----------|-------|---------|-------------|
| `bus_int` | INT | ON | Interrupt request pending flag |
| `int_vec` | Vec | off | Interrupt vector (octal) |
| `int_ipl` | IPL | off | Interrupt priority level |

#### RK11 Disk

| Signal ID | Label | Default | Description |
|-----------|-------|---------|-------------|
| `rk_state` | RK | ON | RK11 state (0=Idle, non-zero means disk transfer in progress) |

### 3.3 Zoom & Scroll Operations

| Operation | Action |
|-----------|--------|
| Mouse wheel | Horizontal zoom (zoom in/out centered on pointer position) |
| Left drag | Horizontal scroll |
| Shift+click | Place A marker |
| Ctrl+click | Place B marker |

When A and B markers are placed, the difference in clock count is shown at the top of the waveform.

### 3.4 Ring Buffer Specification

- Size: 4096 samples (1 sample per clock)
- Format: 160 bits/sample (32 bits × 5 words)

```text
Word0 [31:0]:
  [17:0]  = Unibus physical address (18-bit)
  [18]    = bus_wr
  [19]    = bus_rd
  [21:20] = cpu_cm (00=Kernel, 11=User)
  [22]    = byte_op
  [23]    = trapped
  [24]    = halted
  [25]    = bus_int
  [30:26] = rk_state (5-bit)

Word1 [31:0]:
  [15: 0] = Bus data (16-bit)
  [31:16] = PSW

Word2 [31:0]:
  [15: 0] = PC (virtual)
  [31:16] = Virtual address (before MMU translation)

Word3 [31:0]:
  [ 7: 0] = Interrupt vector (8-bit)
  [15: 8] = Interrupt priority level (8-bit)

Word4 [31:0]:
  Reserved
```

## 4. PC Trigger

The "PC Trigger" panel automatically stops the simulation the moment the CPU reaches the specified PC value.

### 4.1 Setup Procedure

1. Enter the PC value at which you want to stop, in **octal**, in the PC Trigger panel input field.
2. Select a known landmark from the dropdown, or type a value directly.
3. Press the **Set** button.
4. When the simulation reaches that PC while running, it stops automatically.
5. After stopping, press **Resume** to continue.

### 4.2 Known PC List

| Label | PC (octal) | Description |
|-------|-----------|-------------|
| `bootrom entry` | `0173000` | bootrom.v entry point |
| `kernel entry` | `0000000` | Unix V6 kernel m40.s entry |
| `printf(mem=)` | `0004014` | `printf("mem=")` in main.c |
| `user mode RTT` | `0003512` | RTT instruction to user process |
| `login wait` | `0015670` | getty/login key-input wait loop |
| `KW11 vec` | `0000100` | Line clock interrupt vector |
| `RK11 vec` | `0000220` | RK11 disk interrupt vector |
| `TTY RX vec` | `0000060` | DL11 receive interrupt vector |

## 5. Boot Progress Indicator

Immediately after the simulation starts, a "Boot Progress" bar appears and
the kernel boot phases are highlighted step by step.

Typical steps:

```text
[ bootrom ] → [ kernel ] → [ mem= ] → [ user RTT ] → [ login ]
```

Each step turns "complete (green)" when the `pc` signal value in the Logic Analyzer
reaches the known PC. Boot is complete when `login:` appears.

## 6. Event Log Panel

The "Event Log" panel on the right side of the terminal **displays trap events and mode transitions
in chronological order**. While the Logic Analyzer records signal-level waveforms,
the Event Log automatically accumulates semantic-level events, so you can check them
instantly without any configuration.

### 6.1 Display Contents

Each row is one of the following types (newest first, up to 120 entries).

```text
PC      Type              Notes
000320  TRAP             PSW=f000   ← sys call / bus error, etc.
000320  User → Kernel               ← privileged transition via sys call
003104  Kernel → User               ← sys call return (RTT)
000100  User → Kernel               ← KW11 interrupt (no TRAP)
006636  Kernel → User               ← interrupt return
```

| Color | Type | Meaning |
|-------|------|---------|
| Orange | `TRAP PSW=xxxx` | Trap occurred (sys call, bus error, etc.) |
| Blue | `XX → Kernel` | Transition to kernel mode (sys call or interrupt) |
| Green | `Kernel → XX` | Return to user mode (RTT or interrupt return) |

### 6.2 Distinguishing a sys call from an interrupt

If `TRAP` (orange) and `User → Kernel` (blue) appear together at the same PC, it is a **sys call**.
If only `User → Kernel` appears without `TRAP`, it is an **interrupt** (KW11, RK11, TTY).

```text
000320  TRAP             PSW=f000   ─┐ appear together
000320  User → Kernel               ─┘ → confirmed sys call
000100  User → Kernel               ← no TRAP → KW11 interrupt
```

### 6.3 Common Trap Causes

| Vector (octal) | Cause |
|---------------|-------|
| `004` | Bus error |
| `010` | Illegal instruction |
| `034` | EMT (Unix V6 sys call) |
| `040` | TRAP instruction |

### 6.4 When to Use Event Log vs. Logic Analyzer

| | Event Log | Logic Analyzer |
|---|-----------|----------------|
| Information granularity | Semantic level (which trap, how many times) | Signal level (bus waveforms) |
| Configuration | None required, auto-accumulates | Channels and triggers must be set up |
| Best suited for | Tracking abnormal trap frequency and PC | Detailed bus activity around a trap |

### 6.5 exec Capture and Known Limitations

Enabling the **exec** checkbox in the Event Log header automatically clears the log and
starts capturing when `fork(2)` / `exec(11)` is detected, then stops on `exit(1)`.
This is useful for isolating the syscalls belonging to a single command execution.

#### Known Limitations (as of 2026-06-12)

- **exit may not be recorded on the 2nd or 3rd run.**
  When a program calls exec via `sys 0; .word 11` (indirect), the harness PAR
  translation may fail and exec cannot be detected as `exec(11)`.
  In that case the implementation falls back to `fork(2)` detection, but
  close/time and other syscalls from the shell process (`UIPAR0=[1343]` etc.)
  may bypass the filter and appear as noise.
- **Mode transitions (User → Kernel / Kernel → User) have a weak process filter
  and may include transitions from the shell.**
- Even with exec capture enabled, manually toggling the capture switch directly
  will not set the `_pendingUipar0` filter, causing all processes' syscalls to
  be recorded. Use the exec checkbox for automatic start instead.

## 7. Typical Debug Procedures

### Scenario A: Tracking Kernel/User Mode Switches

1. Turn on the `cm` (Mode) signal.
2. Run the simulation.
3. Use the Logic Analyzer to find the moment the background changes from Kernel (light green) to User (light blue).
4. Adding the `psw` signal around the RTT instruction (on return) lets you see the change in PSW[CM].

### Scenario B: Observing RK11 Disk Transfers

1. Turn on `rk_state`, `addr_p`, `bus_rd`, `bus_wr`, and `data`.
2. Turn on the decode lane.
3. Trigger I/O on Unix V6, e.g., `ls /`.
4. The interval where `rk_state` is non-zero is the DMA transfer.
5. In the IO\_RD / IO\_WR bands, you can confirm accesses to RK11 registers (`0o177400`–).

### Scenario C: Confirming Interrupt Timing

1. Turn on `bus_int`, `int_vec`, and `int_ipl`.
2. Run the simulation.
3. Find the moment `bus_int=1` and confirm `int_vec=0o100` (KW11) or `0o220` (RK11).
4. `trapped=1` rises just before control transfers to the trap vector.

### Scenario D: Catching the Unix Startup printf with PC Trigger

1. Select `printf(mem=)` (`0004014`) in PC Trigger and press **Set**.
2. Press **Run**.
3. The simulation stops automatically just before `mem =` is printed to the terminal.
4. Check R0–R5 and SP in the GPR panel to read the register state immediately after kernel initialization.

## 8. Debug Session Examples

### Session 1: Tracing the Unix V6 Boot Sequence

**Goal**: Confirm the PC transitions `bootrom → kernel → printf → user RTT → login` in the Logic Analyzer.

#### Procedure

1. Turn on `pc`, `cm`, `bus_rd`, and `bus_wr`.
2. Turn on the decode lane.
3. **Reset** → send `rkunix` to start the boot.
4. After boot completes, press **Pause**.
5. Zoom out the waveform and look for large changes in `pc` (kernel transition points).

#### What to Look For

- The moment `pc` jumps from around `0o173000` (bootrom) to around `0o000000` (kernel)
  marks the completion of the kernel load.
- The background is light green while `cm=Kernel`, and switches to light blue when `cm=User`.
- KW11 interrupts (`int_vec=0o100`) occur periodically while the kernel is running.

### Session 2: Observing Bus Activity During cc Compilation

**Goal**: Observe RK11 disk accesses and MMU mapping while running `cc hello.c`.

#### Procedure

1. Turn on `rk_state`, `addr_p`, `cm`, and `trapped`.
2. Type `cc hello.c` at the Unix V6 prompt and press Enter.
3. Press **Pause** (or the Freeze button) while compilation is running.
4. In the waveform, find the interval where `rk_state` changes frequently.

#### What to Look For

- Each time the compiler stages (`/bin/cpp`→`/bin/c0`→`/bin/c1`→`/bin/c2`→`/bin/as`→`/bin/ld`)
  are called via exec, `addr_p` changes to new pages (process replacement).
- Long intervals where `rk_state` is non-zero are object file reads/writes.
- User-mode execution (`cm=User`) and `exec` system calls (`cm=Kernel`) alternate.
