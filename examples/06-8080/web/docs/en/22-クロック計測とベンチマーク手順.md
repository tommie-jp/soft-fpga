# 22. Clock Measurement and Benchmark Procedures

> **Replaced with measurements on 2026-10-13**: the outputs in § 2–5 are the actual outputs of compiling and running
> these programs with this procedure on the Linux build (`build/cpm`, Verilator 5.042) of soft-fpga ac6b663. Keep two points in mind.
>
> - The counter advances once per `clk` period and **by 2 per T-state** ([20-サイクルカウンタ.md](20-サイクルカウンタ.md)). Numbers the programs print as "T" are twice the T-state count
> - BDS C `int` is a 16-bit signed integer and the programs print differences with `%d`. A difference above 32767 prints as a negative number (the negative numbers below are this)
>
> So the CALIB, SORT and BENCH numbers cannot be used to check the T-states of a single instruction. To count instruction T-states,
> read the counter from assembly ([20 § 3](20-サイクルカウンタ.md)) or use the Vitest timing tests ([26](26-Vitestタイミングテスト.md)).

Procedures for compiling and running BDS C programs placed in `examples/06-8080/` on CP/M.

- **CYCL.C / CYCL.H** — T-state counter shared library (required by all programs)
- **CALIB.C** — Counter calibration (verifies: 4× IN at 10T each = 40T)
- **SORT.C** — T-state comparison between bubble sort and insertion sort
- **BENCH.C** — Measures IN / OUT / memory read-write / addition / function call
- **FREQ.C** — Measures the simulation's equivalent clock frequency and compares with real 8080A (2 MHz)

## 1. Prerequisites

### 1.1 Boot Disks

| Drive | Image | Contents |
|-------|-------|----------|
| A: | `sw/cpm/disks/cpm22.dsk` | CP/M standard commands, R.COM/W.COM |
| B: | `sw/cpm/disks/bdsc.dsk` | BDS C compiler (`CC.COM`, `CLINK.COM`) |

```bash
# Launch from examples/06-8080/ (the R command looks in the current directory)
cd examples/06-8080
./build/cpm
```

### 1.2 Transferring Source Files

Use `R.COM` to transfer files into the running CP/M session. **Switch to B: first** — BDS C's `CC` looks for `CC2.COM`, and `CLINK` for `C.CCC` etc.,
on the current drive, so compile on B:, where BDS C lives (typing `B:CC` from A: stops with "Can't find CC2.COM" / "Can't find 0/A:C.CCC"; checked on 2026-10-13).

```text
A>B:
B>R CYCL.H
B>R CYCL.C
B>R CALIB.C
B>R SORT.C
B>R BENCH.C
B>R FREQ.C
```

> **Alternative (cpmtools)**: Stop `cpm` first, then copy files from the host in one batch.
>
> ```bash
> for f in CYCL.H CYCL.C CALIB.C SORT.C BENCH.C FREQ.C; do
>   cpmcp -f ibm-3740 sw/cpm/disks/bdsc.dsk $f 0:$f
> done
> ```

## 2. CALIB.C — Counter Calibration

### 2.1 Compile

```text
B>CC CYCL.C
B>CC CALIB.C
B>CLINK CALIB CYCL
```

> `CYCL.CRL` only needs to be compiled once and can be reused by SORT.C and BENCH.C.

### 2.2 Run

```text
B>CALIB
```

### 2.3 Measured Output (2026-10-13)

```text
=== Cycle Counter Calibration  Ver. 0.10 ===

overhead   t0=562    t1=2924   diff=2362 T
empty 100x  t0=562    t1=-9930  diff=-10492 T  (-104 T/iter)
4x IN 100x  t0=562    t1=19798  diff=19236 T  (192 T/iter)
  => +296 T/iter vs empty (~40 expected)
```

**Interpretation**:

- The `overhead` of 2362 is a counter value, i.e. 1181 T-states: two `cycl_read()` calls (function call plus four `IN`s)
- `empty 100x` went negative because the difference exceeded 32767 (if it wrapped 16 bits once, it is 65536 − 10492 = 55044 counts ≈ 27500 T, about 275 T per iteration; how many times it wrapped cannot be told from this output)
- `4x IN` (192) and the resulting `+296` contain the same overflow, so they do not confirm "4 INs = 40 T"
- The original criterion "`+40 T` means the counter works" cannot be applied to this output

## 3. SORT.C — Bubble Sort vs Insertion Sort

### 3.1 Compile

```text
B>CC SORT.C
B>CLINK SORT CYCL
```

(Reuse `CYCL.CRL` compiled in § 2.1)

### 3.2 Run

```text
B>SORT
```

### 3.3 Measured Output (2026-10-13)

```text
=== Sort Benchmark  N=16 ===

Worst case (reverse):
  bubble sort         : -8000 T
  insertion sort      : 16178 T

Random data:
  bubble sort         : -15488 T
  insertion sort      : -2238 T
```

**Interpretation**:

- The program runs with N=16 (not N=32 as originally written)
- Negative numbers are 16-bit overflow. All four exceed 32767 counts (about 16000 T), so this output cannot compare the two sorts
- The original "insertion sort is about 35% faster on reversed input" was a prediction and is not confirmed by this output

## 4. BENCH.C — I/O, Memory, and Arithmetic Benchmark

### 4.1 Compile

```text
B>CC BENCH.C
B>CLINK BENCH CYCL
```

### 4.2 Run

```text
B>BENCH
```

### 4.3 Measured Output (2026-10-13)

```text
=== 8080 Benchmark  N=100 ===

Loop base: -104 T/iter

  4x IN           : 296 T extra (exp 40)
  4x OUT          : -214 T extra (exp 40)
  4x mem rd       : 391 T extra (exp ~28)
  4x mem wr       : 337 T extra (exp ~28)
  8x int add      : -174 T extra (exp ~32)
  C func call     : 74 T extra (exp ~27)
```

**Interpretation**: even the loop baseline (`Loop base`) is negative from 16-bit overflow, so the `extra` numbers cannot be compared with "exp".
The original criterion "within ±2T of exp means the RTL is accurate" cannot be applied to this output.
`inp()` and array accesses include BDS C function calls and address arithmetic, so even without overflow they would not equal a single instruction in the table below.

The table below lists the expected value of a single instruction (T-states from the Intel datasheet).

| Target | Instruction | Expected |
|--------|-------------|----------|
| `inp()` × 4 | `IN p` × 4 | 40T (= 10T × 4) |
| `outp()` × 4 | `OUT p` × 4 | 40T |
| `char` read × 4 | `MOV A,M` × 4 | 28T (= 7T × 4) |
| `char` write × 4 | `MOV M,A` × 4 | 28T |
| `int` add × 8 | `ADD r` × 8 | 32T (= 4T × 8) |
| C function call | `CALL nn + RET` | 27T (= 17T + 10T) |

## 5. FREQ.C — Simulation Equivalent Clock Frequency

### 5.1 Compile

```text
B>CC FREQ.C
B>CLINK FREQ CYCL
```

(Reuse `CYCL.CRL` compiled in § 2.1)

### 5.2 Run

```text
B>FREQ
```

### 5.3 Measured Output (2026-10-13)

```text
=== Equivalent Clock Frequency Ver. 0.1.2 ===
  Measuring : 5000-iter loop (~125 kT)

  Simulated :     7,048,072 Hz
  Real 8080A:     2,000,000 Hz
  vs 8080A  : 352%
```

This number depends on the speed of the PC (the above is the Linux build on WSL2; a browser gives a different number).

**Interpretation**:

- `Simulated` — frequency derived from wall-clock time (`FSTA` / `FLAT` ports) and the counter. **The counter counts `clk`, so this is the `clk` frequency**;
  the T-state rate (the value to compare with the 8080's 2 MHz) is half of it (about 3.5 MHz, about 176% of 2 MHz, in the example above)
- `Real 8080A` — comparison baseline (fixed at 2 MHz)
- `vs 8080A` — `Simulated / 2 MHz × 100` (Verilator depends on host CPU speed,
  so values of several hundred to several thousand percent are normal)

**Measurement principle**:

```c
freq_start();          // OUT 34h: record wall clock + cycle counter
for (i = 0; i < N; i++) ;  // empty loop, N=5000
freq_latch();          // OUT 38h: finalize Hz from elapsed time
mhz = freq_mhz();     // IN 34h/35h
khz = freq_khz();     // IN 36h
hz  = freq_hz();      // IN 37h
```

> When MHz > 30, `vs 8080A` is rounded to 30,000 kHz to avoid overflowing the 16-bit `int`.

## 6. All-in-One Command Sequence

To compile and run all programs in one go (on B:, see § 1.2):

```text
A>B:
B>R CYCL.H
B>R CYCL.C
B>R CALIB.C
B>R SORT.C
B>R BENCH.C
B>R FREQ.C
B>CC CYCL.C
B>CC CALIB.C
B>CC SORT.C
B>CC BENCH.C
B>CC FREQ.C
B>CLINK CALIB CYCL
B>CLINK SORT CYCL
B>CLINK BENCH CYCL
B>CLINK FREQ CYCL
B>CALIB
B>SORT
B>BENCH
B>FREQ
```

## 7. BDS C Limitations (Caveats)

| Limitation | Details |
|------------|---------|
| No `long` | Only 16-bit signed `int`. Differences are printed with `%d`, so they are correct only up to 32767 counts (about 16000 T) |
| 8-character identifier limit | `measure_overhead` and `measure_empty` collide; renamed to `do_ovhd` / `do_empty` |
| No `#asm`/`#endasm` | NOP replaced by `inp(0x10)` × 4 to insert 40T |
| Compile extension | `.C` → `.CRL` (intermediate) → `CLINK` → `.COM` |
