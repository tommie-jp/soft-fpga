### 2.2 Klaus Dormann 6502 Functional Test

An industry-standard 6502/65C02 test ROM. If the CPU is correct it enters a trap loop at a specific address.
On failure it halts at a different address, indicating which instruction group is broken.

| Item | Details |
| --- | --- |
| Repository | [Klaus2m5/6502_65C02_functional_tests](https://github.com/Klaus2m5/6502_65C02_functional_tests) |
| License | GPL v3 |
| File used | `6502_functional_test.bin` (NMOS / 64 KB flat) |

```bash
# Run locally
verif/dormann/run.sh

# Via Docker (same environment as CI)
docker compose -f docker/compose.yml run --rm dormann
```

Output on success:

```text
PASS: trapped at $3469 after 96241373 cycles
```

On failure, `FAIL: trapped at $XXXX` is printed and the PC value identifies which test failed.

#### Pass Criteria

| Variant | Success trap |
| --- | --- |
| 6502 version | Infinite loop at `$3469` |
| 65C02 version | Similar trap address (see comment at top of ROM) |

#### Pass/Fail Detection Logic

```cpp
// Pass → PC = $3469 with JMP *
// Fail → JMP * at a different address (trap)
uint16_t last_pc = 0xFFFF;
while (true) {
    step();
    uint16_t pc = get_pc();
    if (pc == last_pc) {
        printf(pc == 0x3469 ? "PASS\n" : "FAIL at $%04X\n", pc);
        break;
    }
    last_pc = pc;
}
```

hoglet67/cpu_65c02.v has already passed the Dormann 65C02 test (noted in its README).

### 2.3 Woz Monitor Integration Test

`verif/wozmon/` contains a Verilator-native C++ integration test.
The Verilog RTL is compiled with Verilator, the wozmon ROM is embedded, and the test runs automatically.

```bash
# Run locally
verif/wozmon/run.sh

# Via Docker (same environment as CI)
docker compose -f docker/compose.yml run --rm wozmon
```

Output on success:

```text
test_wozmon:  13 PASS / 0 FAIL
test_programs: 34 PASS / 0 FAIL
```

#### Test Cases

| # | Description | Expected result |
| --- | --- | --- |
| 1 | Boot prompt | `\` is displayed |
| 2 | `FF00` single-address read | `FF00: D8` |
| 3 | `FF00.FF0F` range dump | 2 lines × 8 bytes hex dump |
| 4 | `0300: A9 55 4C 00 03` write | Echo confirmed |
| 5 | `0300.0304` read-back | `0300: A9 55 4C 00 03` |
| 6 | `0300: A9 55 85 00 A9 AA 85 01 00` write | Echo confirmed |
| 7 | `0300.0308` dump | 2 lines (8+1 bytes) confirmed |
| 8 | `0000.00FF` full zero-page dump | First and last lines are `00` |
| 9 | `0300R` execute → verify ZP write | `$00=55`, `$01=AA` |

#### Implementation Notes

After a normal command, wozmon does **not** re-output the `\` prompt.
The `\` character is only output via `$FF1A` (the ESCAPE label) at boot time and after ESC.
After a normal command, execution jumps directly to `$FF1F`, outputs only CR, and returns to GETCHAR.
Therefore, automated tests cannot use `\` as a "command complete" signal;
pass/fail is determined by the appearance of the result string (e.g. `FF00: D8`).

## 3. Manual Verification

### 3.1 Manual Test Program Collection (via wozmon)

> **Automated test coverage**: `verif/wozmon/test_programs` automatically verifies all 12 programs.
> The IRQ vector is pointed to $FF00; BRK-terminated program variants are run and
> pass/fail is determined by RAM side-effects.
> During manual execution, observe internal signals using the Logic Analyzer / Register Panel.

wozmon input format: write with `0300: AA BB CC ...`, then run with `0300R`.

#### 3.1.1 Minimal Check: LDA Loop (5 bytes)

```text
0300: A9 55 4C 00 03
```

```asm
LDA #$55
JMP $0300
```

- Register Panel: A is always `$55`
- Logic Analyzer: `sync` lights up every 2 clocks; `addr` cycles `$0300→$0301→$0300…`

---

#### 3.1.2 Memory Read/Write (9 bytes)

```text
0300: A9 AA 85 10 A5 10 4C 00 03
```

```asm
LDA #$AA
STA $10     ; WE=1, write to addr=$0010
LDA $10     ; WE=0, read from addr=$0010
JMP $0300
```

- Logic Analyzer: a red segment for `we=1` appears at `$0010`
- Logic Analyzer: the next `LDA` reads back the same address with `we=0`

---

#### 3.1.3 Stack Push/Pop (11 bytes)

```text
0300: A9 11 48 A9 22 48 68 68 4C 00 03
```

```asm
LDA #$11
PHA          ; SP: FF→FE, write to $01FF
LDA #$22
PHA          ; SP: FE→FD, write to $01FE
PLA          ; SP: FD→FE, read from $01FE (A=$22)
PLA          ; SP: FE→FF, read from $01FF (A=$11)
JMP $0300
```

- Register Panel: SP transitions `FF→FE→FD→FE→FF`
- Logic Analyzer: alternating `we=1/0` accesses to `$01FF` and `$01FE`

---

#### 3.1.4 Flags and Branches (11 bytes)

```text
0300: A9 FF 69 01 B0 03 4C 10 03 4C 00 03
```

```asm
LDA #$FF
ADC #$01     ; A=$00, C=1, Z=1, N=0
BCS $030C    ; C=1 so branch is taken
JMP $0310    ; never reached (would indicate an error)
JMP $0300
```

- Register Panel: verify `C=1 Z=1` in Flags
- Logic Analyzer: `sync` jumps on the `BCS` taken-branch cycle

---

#### 3.1.5 Indexed Addressing (13 bytes + 5 bytes data)

```text
0320: 11 22 33 44 55
0300: A2 00 BD 20 03 E8 E0 05 D0 F8 4C 00 03
```

```asm
; Place data at $0320 first, then run 0300R
LDX #$00
LDA $0320,X  ; read with X=0,1,2,3,4
INX
CPX #$05
BNE $0302
JMP $0300
```

- Logic Analyzer: `addr` appears sequentially as `$0320→$0321→$0322→$0323→$0324`
- Register Panel: X counts `0→1→2→3→4→0`

---

#### 3.1.6 JSR / RTS (Subroutine call, 12 bytes)

```text
0300: 20 08 03 20 08 03 4C 00 03 E8 60
```

```asm
; $0300
JSR $0308    ; push PC+2 onto stack (2 bytes), jump to $0308
JSR $0308    ; second call
JMP $0300
; $0308
INX          ; increment X
RTS          ; pop return address from stack
```

- Register Panel: X increments by 1 per call (`$01`→`$02`…)
- Logic Analyzer: JSR shows writes to `$01FE/$01FF`; RTS shows reads
- Logic Analyzer: JSR takes 6 cycles, RTS takes 6 cycles (longer `sync` intervals)

---

#### 3.1.7 Logical Operations (AND / ORA / EOR, 12 bytes)

```text
0300: A9 FF 29 0F 09 F0 49 AA 4C 00 03
```

```asm
LDA #$FF
AND #$0F     ; A=$0F (keep lower 4 bits only)
ORA #$F0     ; A=$FF (set upper 4 bits)
EOR #$AA     ; A=$55 (XOR bit-flip)
JMP $0300
```

- Register Panel: A transitions `$FF→$0F→$FF→$55`
- Register Panel: N flag transitions `1→0→1→0`

---

#### 3.1.8 Shift and Rotate (ASL / LSR / ROL / ROR, 15 bytes)

```text
0300: A9 01 0A 0A 0A 4A 38 2A 6A 4C 00 03
```

```asm
LDA #$01
ASL A        ; A=$02  C=0
ASL A        ; A=$04  C=0
ASL A        ; A=$08  C=0
LSR A        ; A=$04  C=0
SEC          ; set C=1
ROL A        ; A=$09  C=0 (rotate left, C enters bit0)
ROR A        ; A=$04  C=1 (rotate right)
JMP $0300
```

- Register Panel: verify the correlation between A bit pattern and the C flag
- Logic Analyzer: 2-cycle `sync` interval per instruction (fetch + execute)

---

#### 3.1.9 Page-Cross Penalty Cycle (13 bytes + data)

```text
03FF: 42
0300: A2 01 BD FE 02 A0 01 B9 FE 02 4C 00 03
```

```asm
; $02FF: data (page cross occurs with addr $02FE + X=1)
LDX #$01
LDA $02FF,X  ; reads $0300 ($02FF + 1 = $0300 = page cross) → 5 cycles
LDY #$01
LDA $02FF,Y  ; same → 5 cycles (would be 4 cycles without page cross)
JMP $0300
```

- Logic Analyzer: `LDA abs,X` becomes 5 cycles on a page cross (one extra `sync` interval)
- Logic Analyzer: a spurious read to `$02FF` (extra access) is visible

---

#### 3.1.10 RMW Instructions (INC / DEC memory, 11 bytes)

```text
0300: A9 00 85 20 E6 20 E6 20 C6 20 4C 00 03
```

```asm
LDA #$00
STA $20      ; initialise $20 = $00
INC $20      ; $20 = $01 (5-cycle Read→Modify→Write)
INC $20      ; $20 = $02
DEC $20      ; $20 = $01
JMP $0300
```

- Logic Analyzer: a single `INC` produces consecutive **read → write** accesses to `addr=$0020` (RMW)
- Logic Analyzer: a spurious write to the same address occurs for one cycle immediately before the real write (authentic chip behavior)

---

#### 3.1.11 Zero-Page X Indexed (12 bytes)

```text
0050: 11 22 33 44
0300: A2 00 B5 50 E8 E0 04 D0 F9 4C 00 03
```

```asm
; Place data at $0050–$0053 first
LDX #$00
LDA $50,X    ; ZP + X access (reads $50–$53 in sequence)
INX
CPX #$04
BNE $0302
JMP $0300
```

- Logic Analyzer: address walks `$0050→$0051→$0052→$0053` within the zero page
- Logic Analyzer: zero-page addressing is 1 byte shorter and 1 cycle faster than absolute (4 cycles)

---

#### 3.1.12 Indirect Indexed ((zp),Y Addressing, 11 bytes)

```text
0400: 55
0020: 00 04
0300: A0 00 A9 00 91 20 C8 C0 04 D0 F9 4C 00 03
```

```asm
; Place pointer $0400 at $0020/$0021 first
; Use $0400 as a clear buffer
LDY #$00
LDA #$00
STA ($20),Y  ; ($20) = $0400, Y=0 → write to $0400+0
INY
CPY #$04
BNE $0302
JMP $0300
```

- Logic Analyzer: two-stage access is visible — ZP read (`$0020`·`$0021`) followed by pointer dereference (`$0400+Y`)
- Logic Analyzer: indirect address resolution takes 6 cycles total

### 3.2 Integer BASIC Smoke Test

> **Automated test coverage**: `verif/wozmon/test_programs` §3.2 performs automated verification.
> It runs `E000R` → `PRINT 2+2` and confirms that the output contains `4`.

Integer BASIC ROM ($E000–$EFFF) is embedded in harness.cpp.
It can be launched from wozmon with `E000R`, making it the most intuitive test for visual confirmation by a human.

```text
1. Start the simulator → confirm \ prompt
2. E000R → BASIC starts (no prompt displayed)
3. PRINT 2+2  → 4  ← automatically verified
4. PRINT 10*10 → 100
5. PRINT 32767+1 → confirm overflow behavior
```

What this verifies: multiply/divide/add routines, string output, input loop.

## 4. Future Test Plans

### 4.1 Tom Harte ProcessorTests (Cycle Accuracy)

A test suite of 10,000 cases per opcode, each defining the initial state, expected final state, and memory-access sequence in JSON format.

#### What is Verified

- Address bus (AB), data bus (DB), and WE values for each cycle
- Register state after execution (A, X, Y, SP, PC, P)
- Memory contents after execution

#### Implementation Approach

```text
Create a C++ test driver under verif/tb_unit/
  → Load JSON, compare AB/DB/WE against eval() result cycle by cycle
  → On failure, print cycle number, expected value, and actual value
```

**Implementation cost**: Medium (requires a JSON parser; use nlohmann/json or equivalent)

**Reference**: [https://github.com/TomHarte/ProcessorTests/tree/main/nes6502](https://github.com/TomHarte/ProcessorTests/tree/main/nes6502)
(A 65C02 variant also exists in the same repository)
