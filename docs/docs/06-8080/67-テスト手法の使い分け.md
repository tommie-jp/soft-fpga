# 67. テスト手法の使い分け

8080/CP/M 実装には目的の異なる複数のテスト手法がある。本書はそれぞれの特徴・向き不向き・
使い分けを横断的に整理する。個別の仕様・手順は各 doc（[10](10-テスト仕様書.md) /
[13](13-テスト手順.md) / [26](26-Vitestタイミングテスト.md)）を参照。

## 1. 概要

テスト対象は「層」が異なる。下から RTL 信号 → CPU コア動作 → 信号可視化 → ブラウザ UI。
1 つの手法で全層を見ようとすると遅く脆くなるため、層ごとに最適な手法を使い分ける。

```text
ブラウザ UI / 可視化      … Playwright (Web E2E)
信号値・タイミングの可視化  … Vitest (wasm + ring buffer)
CPU コア + BDOS/BIOS 動作  … ネイティブ main_linux (cpm バイナリ)
Verilog RTL 信号レベル     … cocotb
```

## 2. 手法一覧

| 手法 | 対象層 | 実行環境 | 速度 | doTest | 主なファイル |
|------|--------|----------|------|--------|-------------|
| cocotb | RTL 信号 | Verilator（Python駆動） | 速 | [01] | `verif/cocotb/06-8080/` |
| ネイティブ `cpm` | CPU+BDOS+BIOS | Verilator ネイティブ | 最速 | [05] | `examples/06-8080/cxx/main_linux.cpp` |
| Vitest | 信号値・タイミング | Node + wasm | 速 | [04] | `examples/06-8080/tests/` |
| Playwright | ブラウザ UI/可視化 | Chromium + wasm | 遅 | 06・07 | `verif/web/test_8080.py` |

## 3. 各手法の詳細

### 3.1 cocotb（RTL 信号レベル）

- **対象**: Verilog の信号そのもの（`f1`/`f2` 二相クロック、`dbg_sync`、バスタイミング）。
  `cpm_top` をラップせず vm80a を直接 DUT にもできる。
- **向き**: RTL 配線・タイミングの検証、`pin_int` を直接制御する**割り込みシーケンス**のテスト。
- **不向き**: CP/M アプリの実行（重い）、可視化層。

### 3.2 ネイティブ `cpm`（CPU コア + CP/M）

C++ ハーネス経由で CPU コア・BDOS・BIOS を最速で回す。モードが豊富:

- `--test` … スモーク（2 バイト出力）
- `--run-test` … 全命令テストスイート（20 グループ P/F）
- `--boot-test` … CP/M 起動（A> 検出）
- `--exec <cmd>` … 単一コマンド実行＋完了語検出（8080EX1 等）
- `--cpm-script <file>` … **シナリオ駆動**（`!expect`/`!assert` 等で複数コマンド＋アサート）
- `--bare-test` … ベアメタル binary
- `--ddt-ctrlc-test` … DDT Ctrl+C ウォームブート

- **向き**: 命令正確性、CP/M コマンド機能、ファイル I/O、コンパイラ（BDS C）。
  高速で CI 安定、シナリオファイルは宣言的で網羅しやすい。
- **不向き**: UI/可視化、ブラウザ固有の挙動。

### 3.3 Vitest（信号可視化・タイミング）

wasm の ring buffer を読み、SYNC エッジでマシンサイクルに分割して検証する。

- **向き**: T-state 数・マシンサイクル数・各サイクル T 数・レジスタ値・フラグ・バス信号など
  「**可視化の正確性**」（このプロジェクトの核心価値）の回帰防止。
- **不向き**: アプリ実行、UI 操作、ディスク I/O。

### 3.4 Playwright（ブラウザ E2E）

実ブラウザで xterm・Web Worker・wasm・Logic Analyzer 描画・WASM FS・sim API を通しで検証。

- **向き**: UI・可視化・SharedArrayBuffer 経路など**ネイティブでは見えない層**の確認、実環境スモーク。
- **不向き**: 大量網羅（Playwright 起動 + wasm + RAF で遅い）。

## 4. CP/M へテキスト/コマンドを送る手段

同じ「コマンドを送る」でも入口が異なる。

| 手段 | 層 | 用途 |
|------|----|----|
| `--cpm-script` の通常行 + `!expect`/`!assert` | ネイティブ | CP/M コマンドの機能網羅（宣言的・最速） |
| `--exec <cmd>` | ネイティブ | 単一コマンド + 完了語検出（エクササイザ向け） |
| `sim.sendString(str)` / `send_string(s)` | Web sim API | JS の getRegs/readMem 等と組み合わせた検証 |
| `send_cmd(page, cmd)` | Playwright | xterm 入力欄へ直接タイプ（実 UI 経路） |
| Web `!script`/`!expect` マクロ | ブラウザ UI | 対話デモ・手動操作の自動化 |

## 5. 使い分けの指針

- **CPU 命令・フラグ・タイミングの正しさ** → ネイティブ `--run-test` / 8080EX1、または Vitest
- **CP/M コマンド・ファイル I/O・コンパイラの動作** → ネイティブ `--cpm-script`（本命）
- **信号可視化（T-state / M-cycle / レジスタ）の正確性** → Vitest
- **RTL 配線・割り込みシーケンス** → cocotb（vm80a 直接 DUT）
- **ブラウザ UI・可視化描画・実環境スモーク** → Playwright（少数のみ）

原則: **機能の正しさはネイティブ/cocotb で網羅し、ブラウザ固有の振る舞いだけ Web で薄く確認する**。
CP/M コマンドや BDS C の網羅を Playwright で行うのは遅く過剰。逆に、xterm 表示や Logic Analyzer
描画の確認をネイティブで行うことはできない。
