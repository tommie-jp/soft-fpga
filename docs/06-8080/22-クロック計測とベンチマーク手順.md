# 22. クロック計測とベンチマーク手順

> **2026-10-13 に実測へ置き換えた**: § 2〜5 の出力は、soft-fpga ac6b663 の Linux 版 (`build/cpm`、Verilator 5.042) で
> この手順どおりにコンパイルして走らせた実際の出力。数を読む前に 2 点を知っておく。
>
> - カウンタは `clk` 1 周期ごとに 1 増え、**1 T ステートで 2 増える** ([20-サイクルカウンタ.md](20-サイクルカウンタ.md))。プログラムが「T」と書いて出す数は T ステート数の 2 倍
> - BDS C の `int` は 16 ビットの符号付きで、プログラムは差を `%d` で出す。差が 32767 を越えると負の数になる (下の出力の負の数はこれ)
>
> このため CALIB・SORT・BENCH の数は、命令 1 つの T ステートを確かめる用途には使えない。命令の T ステートを数えるなら、
> アセンブラからカウンタを読む ([20 の § 3](20-サイクルカウンタ.md)) か、Vitest のタイミングテスト ([26](26-Vitestタイミングテスト.md)) を使う。

`examples/06-8080/` に置いた BDS C プログラムを CP/M 上でコンパイル・実行する手順。

- **CYCL.C / CYCL.H** — T ステートカウンタ共通ライブラリ（全プログラムに必要）
- **CALIB.C** — カウンタ動作確認（IN 命令 10T × 4 = 40T を実測）
- **SORT.C** — バブルソート vs 挿入ソートの T ステート比較
- **BENCH.C** — IN / OUT / メモリ読み書き / 加算 / 関数呼び出しの計測
- **FREQ.C** — シミュレーション等価クロック周波数を実測し、実機 8080A (2 MHz) と比較

## 1. 前提

### 1.1 起動ディスク

| ドライブ | イメージ | 内容 |
|---------|---------|------|
| A: | `sw/cpm/disks/cpm22.dsk` | CP/M 標準コマンド, R.COM/W.COM |
| B: | `sw/cpm/disks/bdsc.dsk` | BDS C コンパイラ (`CC.COM`, `CLINK.COM`) |

```bash
# examples/06-8080/ から起動する（R コマンドがカレントディレクトリを参照するため）
cd examples/06-8080
./build/cpm
```

### 1.2 ソースファイルの転送

`R.COM` を使って実行中の CP/M に転送する。**B: に移ってから転送する** — BDS C の `CC` は `CC2.COM` を、`CLINK` は `C.CCC` などを
今いるドライブで探すので、コンパイルは BDS C の入った B: で行う (A: から `B:CC` と打つと「Can't find CC2.COM」「Can't find 0/A:C.CCC」で止まる。2026-10-13 に確かめた)。

```text
A>B:
B>R CYCL.H
B>R CYCL.C
B>R CALIB.C
B>R SORT.C
B>R BENCH.C
B>R FREQ.C
```

> **別の方法 (cpmtools)**: `cpm` を停止してからホスト側で一括コピーする。
>
> ```bash
> for f in CYCL.H CYCL.C CALIB.C SORT.C BENCH.C FREQ.C; do
>   cpmcp -f ibm-3740 sw/cpm/disks/bdsc.dsk $f 0:$f
> done
> ```

## 2. CALIB.C — カウンタ動作確認

### 2.1 コンパイル

```text
B>CC CYCL.C
B>CC CALIB.C
B>CLINK CALIB CYCL
```

> `CYCL.CRL` は 1 回コンパイルすれば使い回せる。SORT.C / BENCH.C でも同じ CYCL.CRL を使う。

### 2.2 実行

```text
B>CALIB
```

### 2.3 実測の出力 (2026-10-13)

```text
=== Cycle Counter Calibration  Ver. 0.10 ===

overhead   t0=562    t1=2924   diff=2362 T
empty 100x  t0=562    t1=-9930  diff=-10492 T  (-104 T/iter)
4x IN 100x  t0=562    t1=19798  diff=19236 T  (192 T/iter)
  => +296 T/iter vs empty (~40 expected)
```

**読み方**:

- `overhead` の 2362 はカウンタの値で、T ステートでは 1181 T。`cycl_read()` 2 回の呼び出し (関数呼び出しと 4 回の `IN`) のぶん
- `empty 100x` は差が 32767 を越えて負になった (16 ビットを 1 周だけ回ったとすれば 65536 − 10492 = 55044 カウント = 約 27500 T、1 回あたり約 275 T。何周したかはこの出力からは決められない)
- `4x IN` の 192 と、その差の `+296` も同じあふれを含むので、「IN 4 本 = 40 T」の確かめにはならない
- 初版にあった「`+40 T` ならカウンタ正常」の判定は、この出力では使えない

## 3. SORT.C — バブルソート vs 挿入ソート

### 3.1 コンパイル

```text
B>CC SORT.C
B>CLINK SORT CYCL
```

（`CYCL.CRL` は § 2.1 でコンパイル済みのものを再利用）

### 3.2 実行

```text
B>SORT
```

### 3.3 実測の出力 (2026-10-13)

```text
=== Sort Benchmark  N=16 ===

Worst case (reverse):
  bubble sort         : -8000 T
  insertion sort      : 16178 T

Random data:
  bubble sort         : -15488 T
  insertion sort      : -2238 T
```

**読み方**:

- プログラムは N=16 で回す (初版の N=32 ではない)
- 負の数は 16 ビットのあふれ。4 つとも 32767 カウント (約 16000 T) を越えているので、この出力から 2 つのソートの速さは比べられない
- 初版の「逆順で挿入ソートが約 35% 速い」は予想で、この出力では確かめられない

## 4. BENCH.C — I/O・メモリ・演算計測

### 4.1 コンパイル

```text
B>CC BENCH.C
B>CLINK BENCH CYCL
```

### 4.2 実行

```text
B>BENCH
```

### 4.3 実測の出力 (2026-10-13)

```text
=== 8080 Benchmark  N=100 ===

Loop base: -104 T/iter

  4x IN           : 296 T extra (exp 40)
  4x OUT          : -214 T extra (exp 40)
  4x mem rd       : 391 T extra (exp ~28)
  4x mem wr       : 337 T extra (exp ~28)
  8x int add      : -174 T extra (exp ~32)
  C func call     : 74 T extra (exp ~27)
```

**読み方**: ループの基準 (`Loop base`) からして 16 ビットのあふれで負になっているので、`extra` の数は「exp」と比べられない。
初版の「exp と実測の差が ±2T 以内なら RTL が正確」という判定は、この出力では使えない。
`inp()` や配列の読み書きは BDS C の関数呼び出しやアドレス計算を含むので、あふれが無くても下の表の命令 1 つぶんにはならない。

下の表は命令 1 つぶんの期待値 (Intel のデータシートの T ステート数)。

| 計測対象 | 命令 | 期待値 |
|---------|------|--------|
| `inp()` × 4 | `IN p` × 4 | 40T (= 10T × 4) |
| `outp()` × 4 | `OUT p` × 4 | 40T |
| `char` 読み × 4 | `MOV A,M` × 4 | 28T (= 7T × 4) |
| `char` 書き × 4 | `MOV M,A` × 4 | 28T |
| `int` 加算 × 8 | `ADD r` × 8 | 32T (= 4T × 8) |
| C 関数呼び出し | `CALL nn + RET` | 27T (= 17T + 10T) |

## 5. FREQ.C — シミュレーション等価クロック周波数計測

### 5.1 コンパイル

```text
B>CC FREQ.C
B>CLINK FREQ CYCL
```

（`CYCL.CRL` は § 2.1 でコンパイル済みのものを再利用）

### 5.2 実行

```text
B>FREQ
```

### 5.3 実測の出力 (2026-10-13)

```text
=== Equivalent Clock Frequency Ver. 0.1.2 ===
  Measuring : 5000-iter loop (~125 kT)

  Simulated :     7,048,072 Hz
  Real 8080A:     2,000,000 Hz
  vs 8080A  : 352%
```

この数は走らせた PC の速さで変わる (上は WSL2 上の Linux 版。ブラウザでは別の数になる)。

**読み方**:

- `Simulated` — ウォールクロック（`FSTA` / `FLAT` ポート）とカウンタから算出した周波数。**カウンタは `clk` を数えるので、これは `clk` の周波数**で、
  T ステートの速さ (8080 の 2 MHz と比べるべき値) はその半分 (上の例で約 3.5 MHz、2 MHz の約 176%)
- `Real 8080A` — 実機比較基準（2 MHz 固定）
- `vs 8080A` — `Simulated / 2 MHz × 100`（Verilator はホスト CPU 速度に依存するため数百〜数千 % になる）

**計測原理**:

```c
freq_start();          // OUT 34h: ウォールクロック + サイクルカウンタを記録
for (i = 0; i < N; i++) ;  // N=5000 の空ループ
freq_latch();          // OUT 38h: 経過時間から Hz を確定
mhz = freq_mhz();     // IN 34h/35h
khz = freq_khz();     // IN 36h
hz  = freq_hz();      // IN 37h
```

> `vs 8080A` は `int` 16 ビットの上限を避けるため MHz > 30 の場合は 30,000 kHz に丸めて計算している。

## 6. まとめコマンド列

全プログラムを一括でコンパイルして実行する場合 (B: で行う。§ 1.2):

```text
A>B:
B>R CYCL.H
B>R CYCL.C
B>R CALIB.C
B>R SORT.C
B>R BENCH.C
B>R FREQ.C
B>CC CYCL.C
B>CC CALIB.C
B>CC SORT.C
B>CC BENCH.C
B>CC FREQ.C
B>CLINK CALIB CYCL
B>CLINK SORT CYCL
B>CLINK BENCH CYCL
B>CLINK FREQ CYCL
B>CALIB
B>SORT
B>BENCH
B>FREQ
```

## 7. BDS C の制約（注意点）

| 制約 | 内容 |
|------|------|
| `long` 非対応 | `int` 16 ビットの符号付きのみ。差を `%d` で出すので、正しく出るのは 32767 カウント (= 約 16000 T) まで |
| 識別子は 8 文字有効 | `measure_overhead` と `measure_empty` が衝突するため `do_ovhd` / `do_empty` に改名済み |
| `#asm`/`#endasm` 非対応 | NOP の代わりに `inp(0x10)` × 4 で 40T を挿入 |
| コンパイル拡張子 | `.C` → `.CRL`（中間）→ `CLINK` → `.COM` |
