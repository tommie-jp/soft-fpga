# 25. Debug Panel & Logic Analyzer Guide

The RTL simulator includes built-in debug features for real-time observation of the CPU's internal state.
This document explains the **CPU Bar**, **Logic Analyzer**, and **Debug Panel** features.

---

## 1. CPU Bar (Register Display)

A strip panel displayed directly above the terminal.

```text
CPU  A: F0 | F: SZ.a.P1c | BC: 0005 DE: 0080 HL: FFE4 | SP: FE80 | PC: E4A2 [BDOS]  CALL $F200
```

### 1.1 Register Fields

| Field | Description |
|-------|-------------|
| `A` | Accumulator (2 hex digits) |
| `F` | Flag register (8 characters, see table below) |
| `BC` `DE` `HL` | General-purpose register pairs (4 hex digits) |
| `SP` | Stack pointer (4 hex digits) |
| `PC` | Program counter (4 hex digits) |

### 1.2 Flag Display Format

Flags are displayed as 8 characters in the order `SZ.AC.P1C`.

- Uppercase = flag **ON** (set)
- Lowercase = flag **OFF** (clear)

| Position | Flag | Meaning |
|----------|------|---------|
| 1 | `S`/`s` | Sign flag |
| 2 | `Z`/`z` | Zero flag |
| 3 | `.` | Always 0 (unused) |
| 4 | `A`/`a` | Auxiliary Carry |
| 5 | `.` | Always 0 (unused) |
| 6 | `P`/`p` | Parity |
| 7 | `1` | Always 1 (fixed) |
| 8 | `C`/`c` | Carry flag |

Example: `SZ.a.Plc` → Sign, Zero, and Parity are ON; Aux Carry and Carry are OFF.

### 1.3 PC Region Badges

A coloured badge to the right of the PC value indicates the execution region.

| Badge | Address Range | Meaning |
|-------|--------------|---------|
| (none / grey) | 0000–00FF | Page 0 / zero page |
| `TPA` (green) | 0100–DBFF | Transient Program Area |
| `CCP` (blue) | DC00–E3FF | CCP |
| `BDOS` (orange) | E400–F1FF | BDOS |
| `BIOS` (red) | F200–FFFF | Custom BIOS |

### 1.4 Disassembly Display

The mnemonic at the current PC position is displayed in real time (e.g., `CALL $F200`).
Three bytes are read and the full 8080 instruction set is supported.

### 1.5 FROZEN Badge

When the Ring Buffer is frozen, a `FROZEN` badge (red) is displayed.
While frozen, the Logic Analyzer waveform is static and the register display remains at the last snapshot.

## 2. Logic Analyzer (Signal Display)

An oscilloscope-style waveform area located below the CPU Bar.
It renders up to 4096 clocks of signal data recorded in the ring buffer in real time.

### 2.1 Decode Lane (M-Cycle Display)

An **M-CYC decode lane** is shown at the top of the waveform (toggle with the `M-CYC` button).

Each 8080 machine cycle type is shown as a colour-coded band, with the instruction mnemonic
overlaid at the centre of the band.

| Colour | Machine Cycle Type | Meaning |
|--------|--------------------|---------|
| Light blue | FETCH | Instruction fetch (M1 cycle) |
| Light green | MEM RD | Memory read |
| Light orange | MEM WR | Memory write |
| Light red | IO IN | I/O read (IN instruction) |
| Light purple | IO OUT | I/O write (OUT instruction) |

> **Tip**: FETCH bands display the instruction mnemonic (e.g., `MOV A,C`, `CALL`, `RET`) as an overlay,
> letting you see at a glance which instruction is executing at which address.

### 2.2 T-State Grid

A **bold vertical line** is drawn at each M-cycle boundary (T1 = the moment SYNC rises).
At zoom level 4x and above, **thin dashed lines** are also drawn at each T-state boundary.

> Two system clock periods correspond to one T-state.
> The Time Ruler uses "T" as its unit.

### 2.3 Signal Selection

Signals are organised into four groups. Clicking a group name toggles all signals in that group on or off.

#### I/O Group

| Signal | Default | Description |
|--------|---------|-------------|
| `port` | ON | I/O port number (bus [7:0], hex display) |
| `data` | ON | I/O data (bus [23:16], hex display) |
| `io_req` | ON | I/O cycle active (IN or OUT) |
| `io_wr` | ON | OUT instruction (1=OUT, 0=IN) |

#### Control Group

| Signal | Default | Description |
|--------|---------|-------------|
| `DBIN` | off | Data bus input enable (CPU ← bus) |
| `SYNC` | off | Machine cycle start strobe |
| `WR_N` | off | Bus write strobe (active low) |
| `HLDA` | off | Bus hold acknowledge |
| `WAIT` | off | Wait state |
| `INTE` | off | Interrupt enable |

#### Mem Group

| Signal | Default | Description |
|--------|---------|-------------|
| `MEMR` | off | Memory read cycle |
| `MEMW` | off | Memory write cycle |
| `addr` | off | Address bus (16-bit, 4-digit hex display) |

#### Data Group

| Signal | Default | Description |
|--------|---------|-------------|
| `dbus` | off | Data bus (8-bit, 2-digit hex display) |
| `t_state` | off | T-state number (1–63, reset to 1 at the start of each M cycle) |
| `status` | off | 8080 status byte (M-cycle type latched during SYNC cycle) |

### 2.4 Status Byte Values

The `status` signal (Word 4 [7:0]) is the 8080 status byte captured from `cpu_dout` on the rising edge of SYNC.

| Value | Machine Cycle Type |
|-------|--------------------|
| `0xA2` | FETCH (instruction fetch M1) |
| `0x82` | MEM READ (memory read) |
| `0x40` | IO IN (IN instruction) |
| `0x10` | IO OUT (OUT instruction) |
| Other | MEM WRITE (memory write) |

### 2.5 Zoom and Scroll Operations

| Action | Behaviour |
|--------|-----------|
| Mouse wheel | Horizontal zoom (centred on pointer position) |
| Left drag | Horizontal scroll |
| Shift+click | Place A marker |
| Ctrl+click | Place B marker |

Placing A and B markers displays the difference at the top of the waveform (in units of T).

Hovering the cursor shows the T-state number and M-cycle type at that position in a tooltip.

### 2.6 Ring Buffer Specification

- Size: 4096 samples (1 sample per clock)
- Format: 224 bits/sample (32 bits × 7 words)

```text
Word 0 [31:0]:
  [7:0]  = I/O port number
  [8]    = DBIN
  [9]    = SYNC
  [10]   = WR_N
  [11]   = HLDA
  [12]   = WAIT
  [13]   = INTE
  [14]   = MEMR
  [15]   = MEMW
  [23:16]= I/O data (io_dout)
  [24]   = io_req (I/O cycle active)
  [25]   = io_wr (OUT=1 / IN=0)
  [31:26]= T-state number (1–63)

Word 1 [31:0]:
  [15:0] = Address bus (cpu_addr)
  [23:16]= I/O read data (io_din)
  [31:24]= Accumulator A (vm80a acc)

Word 2 [31:0]:
  [7:0]  = F flags (reconstructed from PSW individual bits: S Z 0 AC 0 P 1 C)
  [15:8] = Register B
  [23:16]= Register C
  [31:24]= Register D

Word 3 [31:0]:
  [7:0]  = Register E
  [15:8] = Register H
  [23:16]= Register L
  [31:24]= CPU data bus (dbus)

Word 4 [31:0]:
  [7:0]  = Status byte (latched during SYNC cycle)
  [15:8] = Instruction register IR
  [16]   = f1 (clock φ1)
  [17]   = f2 (clock φ2)
  [20:18]= Machine cycle number (1=M1 … 5=M5, 0=none)

Word 5 [31:0]:
  [15:0] = PC (vm80a r16_pc register value)
  [31:16]= SP (vm80a r16_sp register value)

Word 6 [31:0]:
  [7:0]  = MemWatch 1 (memory value at specified address)
  [15:8] = MemWatch 2
  [23:16]= MemWatch 3
```

## 3. Debug Panel

The Debug Panel below the Logic Analyzer contains three tabs and control buttons.

### 3.1 Tab Switching

| Tab | Contents |
|-----|----------|
| **Stack** | 8 words (16 bytes) of stack contents starting from SP |
| **I/O Log** | History of IN/OUT instructions (up to 200 entries, newest first) |
| **Call Trace** | CALL / RET trace (up to 64 entries, newest first) |

---

### 3.2 Stack Tab

Displays 8 words upward in memory starting from the stack pointer (SP).

```text
SP→  A2 1F  $1FA2
 +2  F2 00  $00F2  BIOS
 +4  00 E4  $E400  BDOS
 ...
```

- The SP→ row is highlighted in yellow.
- If the value corresponds to a known symbol (BOOT, BDOS, CCP, BDOS, BIOS, DMA), the label is also shown.

---

### 3.3 I/O Log Tab

An entry is recorded every time an IN or OUT instruction is issued.

```text
OUT  $01  $41  CONOUT
IN   $00  $00  CONIN
OUT  $12  $02  DSEC
```

| Column | Description |
|--------|-------------|
| `OUT` / `IN` | Direction (red=OUT, blue=IN) |
| `$XX` | Port number |
| `$XX` | Data value |
| Symbol | Port function name (if known) |

For a list of major I/O port symbols, see "[52-メモリマップ.md](52-メモリマップ.md)".

---

### 3.4 Call Trace Tab

CALL and RET instructions are detected and recorded (SYNC rising edge is monitored at the RTL level).

```text
CALL  $E400 → $F200  BIOS
CALL  $E400 → $F203
RET   $F205 → $E403
```

| Column | Description |
|--------|-------------|
| `CALL` / `RET` | Instruction type (blue=CALL, orange=RET) |
| `$XXXX` | Source address (from) |
| `→ $XXXX` | Destination address (to) |
| Symbol | Known label at the destination (BDOS, BIOS, etc.) |

> **Note**: Conditional CALL (`CZ`, `CNZ`, `CC`, …) and conditional RET are also detected,
> but only those that actually branched (executed at the RTL level) are recorded.

---

## 4. Control Buttons

Buttons aligned on the right side of the Debug Panel header.

### 4.1 ❄ Freeze Button

**Freezes** the Ring Buffer.

- **While frozen**: The Logic Analyzer waveform is static. The CPU continues to run.
- **To unfreeze**: Click again to return to "Freeze" state and resume Ring Buffer updates.
- The `FROZEN` badge appears in the CPU Bar while frozen.

**Use case**: Capturing a momentary burst of bus activity as a snapshot.

### 4.2 ▶ Next I/O Button

Automatically pauses at the moment the next **IN or OUT instruction** is issued.

- If the simulation is paused → starts execution and waits for an I/O event.
- After an I/O hit → the simulation auto-pauses.
- Resume with the `Run` button afterwards.

**Use case**: Precisely examining the timing of a specific I/O access.

## 5. Trigger Feature

A feature for automatically pausing the simulation on finer conditions.

### 5.1 Setup Procedure

1. Select a **Trigger type** from the dropdown.
2. Enter an **address/port filter** (leave blank for any).
3. Press the **Set** button.
4. While the simulation is running, it will auto-pause when the trigger condition is met.

### 5.2 Trigger Types

| Value | Type | Description |
|-------|------|-------------|
| `No Trigger` | None | Trigger disabled |
| `On I/O` | I/O | IN or OUT instruction (port filter available) |
| `On CALL` | CALL | CALL instruction (address filter available) |
| `On RET` | RET | RET instruction (address filter available) |
| `On Edge ↑` | Rising edge | 0→1 rising edge on the specified signal bit |
| `On Edge ↓` | Falling edge | 1→0 falling edge on the specified signal bit |

### 5.3 Address/Port Filter

Enter a hexadecimal value in the `addr/port (hex)` field.

- `On I/O` → port number (e.g., `01` for CONOUT only)
- `On CALL` / `On RET` → destination address (e.g., `F200` for BIOS entry only)
- Left blank → responds to all I/O / CALL / RET events

### 5.4 Edge Trigger Configuration

`On Edge ↑` / `On Edge ↓` appear in the dropdown, but selecting them currently shows no
additional fields (Word/Bit specification is not yet implemented).

### 5.5 Clear Button

Cancels the trigger (returns to `No Trigger`).

### 5.6 CL Button (Clear Call Log)

Clears the records in the Call Trace tab.

## 6. Typical Debug Procedures

### Scenario A: Tracing BDOS Calls

1. Open the **Call Trace** tab.
2. Trigger: `On CALL`, address: `0005` (page 0 BDOS entry vector) → **Set**.
   - User programs call BDOS via `CALL $0005`.
   - When CCP or BIOS calls BDOS directly, they use `E406`.
3. Run the simulation → it auto-pauses the moment BDOS is called.
4. Check the return address in the **Stack** tab.
5. Press **CL** to clear the Call Trace, then resume.

### Scenario B: Checking the Value at a Specific I/O Port

1. Open the **I/O Log** tab.
2. Press `▶ Next I/O` to start the simulation.
3. When an I/O event occurs, the simulation auto-pauses → check the direction, port, and data in the I/O Log.
4. Press `Next I/O` repeatedly to follow subsequent I/O events.

### Scenario C: Viewing Bus Patterns as Waveforms

1. Enable `SYNC`, `DBIN`, `io_req`, and `io_wr` via the Logic Analyzer toggles.
2. Enable the decode lane with the `M-CYC` button.
3. Run the simulation.
4. When the activity of interest is over, press **❄ Freeze** to take a snapshot.
5. Confirm the M-cycle transitions (FETCH → MEM RD) and instruction mnemonics in the decode lane.

### Scenario D: Precisely Stopping on a SYNC Rising Edge

To stop the simulation at the start of an instruction fetch (M1 cycle boundary):

1. Trigger: `On Edge ↑`, Word: `0`, Bit: `9` (SYNC) → **Set**.
2. **Run** → stops immediately on the next SYNC rising edge.
3. Observe the signal state just after that T1 in the waveform view.

### Scenario E: Stopping at a Specific Address (e.g., $0300)

To stop the simulation just before executing a routine placed at $0300, the procedure differs
depending on how that entry is reached.

#### Method 1: `On CALL` Trigger (when $0300 is a CALL target)

If $0300 is the entry point of a subroutine called with `CALL $0300`, this is the simplest approach.

1. Trigger: `On CALL`, addr: `0300` → **Set**.
2. **Run** → auto-pauses the moment `CALL $0300` is executed.
3. Check the bus cycles before and after the call in the Logic Analyzer waveform.

#### Method 2: DDT Breakpoint (for JMP targets or fall-through)

When execution arrives via `JMP $0300` or falls through sequentially, use DDT's
`G` command breakpoint syntax (`,addr`).

```text
A>DDT
-G,0300          ← Execute from current PC; stop when PC reaches $0300
```

- DDT returns to its prompt when PC reaches $0300.
- Then press **Pause** and use **❄ Freeze** to lock the waveform.
- Use DDT's `-R` command to inspect the register state at that moment.

> **How it works**: DDT temporarily writes `RST 7` (`0xFF`) to the breakpoint address,
> restores the original instruction byte on hit, and stops. Usable for any RAM address.

#### Method 3: Edge Trigger on Address Bit 8 Rising (simple approximation)

Word 1 [15:0] is the address bus; at $0300, bits 8 and 9 are both 1.

To catch the transition $02FF → $0300 where bit 8 goes from 0 to 1:

1. Trigger: `On Edge ↑`, Word: `1`, Bit: `8` → **Set**.
2. **Run** → stops on the first clock where address bus bit 8 rises.

> **Limitation**: Reacts to any transition to an address with bit 8 set
> ($0100–$01FF, $0300–$03FF, etc.). Since filtering to $0300 specifically is not possible,
> use this as a supplementary method when execution is already confined near $0300
> (e.g., after limiting PC with DDT).

## 7. Debug Session Examples

The following shows actual operation steps and panel output.
Values are typical for a running simulation and may vary slightly depending on speed settings and timing.

---

### Session 1: Tracing the CP/M Cold-Boot Sequence

**Goal**: Use Call Trace to confirm the call order from BOOT → CCP → prompt display immediately after Reset.

#### Procedure

1. Set the **speed** to a low value such as `500 KHz` (so that Call Trace fits on screen more easily).
2. Select the **Call Trace** tab.
3. Trigger: `On CALL`, filter blank → **Set** (stops on any CALL).
4. Press **Reset** → the simulation auto-pauses at the first CALL after a few clocks.
5. While reading the Call Trace, press **Clear** → **Set** repeatedly to advance to the next CALL.
   Alternatively, **Clear** the trigger and **Run** to let it run freely,
   then **Pause** and check the Call Trace.

#### How to Read the Call Trace (example)

```text
CALL  $F200 → $F233        ← BOOT: jump table → actual code
CALL  $F233 → $F20C        ← Sign-on string CONOUT call
RET   $F20C → $F23B
CALL  $F233 → $F20C        ← Next character (repeated)
RET   $F20C → $F23B
  ...  (repeated for each character)
CALL  $F200 → $F21B  BIOS  ← SELDSK(A:) call
RET   $F21B → $F25A
CALL  $DC00 → $DC03  CCP   ← Jump to CCP cold entry
```

#### Observation Points

- During boot, the majority of CALL/RET pairs are within BIOS (`$F2xx`).
- When `CALL $DC00` appears, control passes to CCP and prompt display begins.
- CONOUT (`$F20C`) repeats once per character, allowing you to count the sign-on string length.

---

### Session 2: Observing Disk Access During the `DIR` Command

**Goal**: Use the I/O Log to verify how many times BIOS READ is called and which tracks/sectors are read when `DIR` runs.

#### Procedure

1. Run until the CP/M prompt appears.
2. Select the **I/O Log** tab.
3. Type `DIR` in the terminal and press Enter.
4. Once the directory listing appears, press **Pause**.
5. Read the I/O Log from the top.

#### I/O Log Example

```text
OUT  $15  $00  DDRV    ← Select drive A:
OUT  $11  $02  DTRK    ← Track 2 (first data track, after reserved tracks)
OUT  $12  $00  DSEC    ← Sector 0 (after SECTRAN translation)
OUT  $13  $80  DDMAL   ← DMA address low byte: $80
OUT  $14  $00  DDMAH   ← DMA address high byte: $00 → DMA=$0080
OUT  $10  $00  DCMD    ← Execute READ
IN   $10  $00  DSTS    ← Result OK
OUT  $12  $06  DSEC    ← Next sector (after skewing)
OUT  $10  $00  DCMD    ← Execute READ
IN   $10  $00  DSTS    ← Result OK
  ...  (repeated for each directory block)
OUT  $01  $41  CONOUT  ← Display 'A'
OUT  $01  $2E  CONOUT  ← '.'
OUT  $01  $43  CONOUT  ← 'C'
  ...  (repeated for each filename)
```

#### Observation Points

- DDRV → DTRK → DSEC → DDMAL → DDMAH → DCMD(READ) → DSTS is the standard sequence for one sector read.
- The directory may be read in up to 4 blocks (4 KB) = 32 sectors (depending on the number of entries).
- The section where CONOUT appears consecutively is the filename output. `$0D` (CR) `$0A` (LF) marks the end of each line.

### Session 3: Examining the BDOS Call Chain and Stack Depth

**Goal**: Confirm the call stack when a user program calls `BDOS #9` (print string).

> Try this with MBASIC or another CP/M application running.

#### Procedure

1. Start MBASIC and wait for the `Ok` prompt, then press **Pause**.
2. Trigger: `On CALL`, address: `0005` → **Set** (BDOS entry).
3. **Run** → auto-pauses the moment BDOS is called.
4. Alternately check the **Stack** tab and **Call Trace** tab.

#### CPU Bar Example Immediately After Pausing

```text
CPU  A: 09 | F: sz.a.p1c | BC: 009A DE: 0113 HL: 0000 | SP: FE80 | PC: 0005 [Page0]  JMP $E406
```

- `A=09` is not "BDOS function #9 (print string PUTS)"; the actual function number is in `C=09`.
  In 8080, the BDOS calling convention passes the function number in the `C` register.
  (BC=`009A` → `B=00, C=09`)
- `DE=0113` is the start address of the string to print (a buffer in the TPA).

#### Stack Tab Example

```text
SP→  56 F2  $F256        ← Return address inside BIOS (from BOOT via CCP)
 +2  03 DC  $DC03  CCP   ← RET target from CCP warm entry
 +4  00 01  $0100        ← Near TPA start (MBASIC loader)
 +6  6A E4  $E46A  BDOS  ← Return from previous BDOS call
 +8  00 00  $0000  BOOT  ← (unused slot)
```

From the BIOS, CCP, and BDOS addresses stacked here, you can visually read the
MBASIC → BDOS → BIOS call hierarchy.

#### Call Trace Tab Example (last few entries before pausing)

```text
CALL  $1A3C → $0005        ← MBASIC calls BDOS
CALL  $E40A → $F20C  BIOS  ← BDOS calls CONOUT internally
RET   $F20E → $E40D
CALL  $E40A → $F20C  BIOS
RET   $F20E → $E40D
```

### Session 4: Tracing CONOUT Output One Character at a Time

**Goal**: Use `▶ Next I/O` to confirm the character output by each CONOUT call, one character at a time.

#### Procedure

1. Select the **I/O Log** tab.
2. Leave the Trigger at `No Trigger` (unset).
3. Type `TYPE HELLO.TXT` (or similar) in the terminal and press Enter.
4. Once characters start appearing, press **Pause**, then press `▶ Next I/O` once.
   → Stops the moment the next IN/OUT occurs.
5. Check the top entry in the I/O Log, then press `▶ Next I/O` again to advance to the next character.

#### I/O Log Top Entry Examples (advancing one character at a time)

```text
Stop 1:  OUT  $02  $00  CONST    ← Key-input polling
Stop 2:  OUT  $01  $48  CONOUT   ← Output 'H' (0x48)
Stop 3:  OUT  $01  $45  CONOUT   ← 'E' (0x45)
Stop 4:  OUT  $01  $4C  CONOUT   ← 'L' (0x4C)
Stop 5:  OUT  $01  $4C  CONOUT   ← 'L'
Stop 6:  OUT  $01  $4F  CONOUT   ← 'O' (0x4F)
```

#### Reading the Instruction in the CPU Bar

At the moment of pause, the disassembly field shows `OUT $01` and the PC region shows
`BIOS` (near `$F20C`). This confirms that "the BIOS CONOUT routine is executing an OUT instruction right now."

### Session 5: Capturing a READ Cycle Waveform with the Logic Analyzer

**Goal**: Visualise the I/O bus cycle during a disk READ in the Logic Analyzer.

#### Procedure

1. Enable `SYNC`, `DBIN`, `io_req`, `io_wr`, `port`, and `data` via the Logic Analyzer toggles.
2. Enable the decode lane with the `M-CYC` button.
3. Trigger: `On I/O`, port: `10` (DCMD) → **Set**.
4. **Run** → run `DIR` or similar; the simulation auto-pauses on an OUT to DCMD.
5. Press **❄ Freeze** to lock the snapshot.

#### How to Read the Waveform

The decode lane just before stopping shows the following pattern:

```text
M-CYC:  [FETCH: OUT][MEM RD][IO OUT]
clk:    __ __ __ __ __ __ __ __ __ __ __
SYNC:   _|‾|__|__|__|‾|__|__|‾|__|__|___
DBIN:   __|‾|‾|‾|__|‾|‾|‾|__|__|__|____
io_req: __|__|__|__|__|__|__|__|__|‾|____
io_wr:  __|__|__|__|__|__|__|__|__|‾|____
port:   .......................................10.
data:   .......................................00.
```

- From left in the decode lane: FETCH (OUT instruction fetch) → MEM RD (port number read) → IO OUT.
- The one clock where `io_req=1` and `io_wr=1` is the execution clock for `OUT $10`.
- `port=10, data=00` means "OUT value 00 (READ command) to DCMD port".

### Session 6: Verifying Logic Analyzer Basics with a Minimal Program

**Goal**: Hand-enter a 3-byte program `MVI A, $FF` → `HLT` using DDT
and observe the address bus and control line transitions in the Logic Analyzer.

#### Assembly and Machine Code

```text
; 8080 assembly (equivalent to LD A, $FF in Z80)
0300:  MVI A, $FF   ; 3E FF  — Load 0xFF into register A
0302:  HLT          ; 76     — Stop the CPU
```

| Address | Machine Code | Mnemonic |
|---------|-------------|---------|
| `0300` | `3E` | `MVI A, $FF` (opcode) |
| `0301` | `FF` | Immediate operand |
| `0302` | `76` | `HLT` |

#### Writing Machine Code with DDT

Use DDT's (CP/M standard debugger) `S` (Set memory) command to write one byte at a time.

```text
A>DDT
DDT VERS 2.2
-S0300
0300 00 3E      ← Current value shown; enter new value
0301 00 FF
0302 00 76
0303 00 .       ← Period to exit
```

> **Verify**: If `-D0300,0302` shows `3E FF 76`, the write succeeded.

#### Step Execution with the T Command (recommended)

Running with the `G` command causes `HLT` to halt the CPU and control does not return to DDT.
Instead, use the `T` (Trace) command to execute one instruction at a time and check register
state at each step.

Since `T` does not accept an address argument, first set PC to 0300 with the `XP` command, then run `T`.

```text
-XP
P=F600
P=0300      ← Enter the new PC value
-T
PC=0300 SP=0100 AF=0001 BC=0000 DE=0000 HL=0000
3E FF      MVI A,FF
-T
PC=0302 SP=0100 AF=FF01 BC=0000 DE=0000 HL=0000
76         HLT
-
```

- `XP`: Change PC (current value is shown; enter the new value).
- First `T`: Executes `MVI A, $FF` → confirms `AF=FF01` (A=FF).
- Second `T`: Executes `HLT` → returns DDT to its prompt.

> **Multiple instructions**: Use `-Tn` (e.g., `-T2`) to trace n instructions in sequence.

#### Running with the G Command

You can also run from a specified address using DDT's `G` (Go) command.

```text
-G0300
```

When the `HLT` instruction is reached, the CPU halts.
Control does not return to DDT (per 8080 specification: halted until reset or interrupt).

The CPU Bar displays the `HLT` badge and `A: FF` confirms the result of `MVI A, $FF`.

```text
CPU  A: FF | F: sz.a.p1c | BC: 0000 DE: 0000 HL: 0000 | SP: 0100 | PC: 0303 [TPA]  HLT
```

> **To return**: Press the Reset button to reboot CP/M.

#### Confirming Signal Transitions in the Logic Analyzer

##### 1. Enable Signals

Enable the following signals in the Logic Analyzer.

| Signal | Role |
|--------|------|
| `SYNC` | Machine cycle start (instruction fetch boundary) |
| `DBIN` | Data bus input enable (memory → CPU) |
| `addr` | Address bus (16-bit) |
| `MEMR` | Memory read cycle |
| `t_state` | T-state number (position within M cycle) |

Also enable the decode lane with the `M-CYC` button.

##### 2. Execute

Run `G0300` from DDT.

```text
-G0300
```

The CPU halts at `HLT`. Control does not return to DDT.

##### 3. Lock the Snapshot with Freeze

Press **❄ Freeze** immediately after the `HLT` halt and the waveform freezes,
letting you examine the fetch sequence for all 3 instructions at your own pace.

> **Note**: `MVI A, $FF` → `HLT` generates no I/O, CALL, or RET, so the current trigger
> features (`On I/O` / `On CALL` / `On RET`) cannot stop it in advance.
> Use Freeze for after-the-fact capture.

#### Expected Waveform Pattern

Typical waveform for reading 3 bytes (`3E FF 76`):

```text
M-CYC: [  FETCH: MVI A,FF  ][MEM RD][FETCH: HLT      ]
clk:   __|‾|__|‾|__|‾|__|‾|__|‾|__|‾|__|‾|__
SYNC:  _|‾|__|__|__|‾|__|__|__|‾|__|__|__|___
DBIN:  __|‾|‾|‾|__|‾|‾|‾|__|‾|‾|‾|__|______
MEMR:  __|‾|‾|‾|__|‾|‾|‾|__|‾|‾|‾|__|______
addr:  ..0300....0301....0302................
t_st:  ..1.2.3.4.1.2.3..1.2.3.4............
```

- `addr=0300`, `SYNC=1` → `MVI A` instruction fetch (M1 cycle)
- `addr=0301`, `SYNC=0` → Immediate operand `$FF` read (M2 cycle)
- `addr=0302`, `SYNC=1` → `HLT` instruction fetch (M1 cycle)
- Thereafter `DBIN=0`, `MEMR=0` → CPU halted (HLT state)
- `t_state=1` marks the start of each M cycle (clock where SYNC=1)

#### Observation Points

- `MVI A, $FF` uses **2 machine cycles** (M1 to fetch opcode; M2 to fetch immediate operand).
- `HLT` executes in **1 machine cycle**; thereafter, even though the clock ticks,
  `DBIN` and `MEMR` no longer rise (the bus is released).
- `addr` transitions `0300 → 0301 → 0302` in order, confirming that the fetch sequence
  is traceable in the waveform.
- The FETCH bands in the decode lane overlay the mnemonics `MVI A,FF` and `HLT`,
  making it immediately clear which M cycle corresponds to which instruction.
