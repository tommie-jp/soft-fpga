# 28. C プログラムの最初の命令は無視される不正命令 <a class="qr-link" href="../../../docs/09-PDP11/img/28-QR.png">QR</a>

UNIX Version 6 のカーネルには、C で書かれたすべてのプログラムに関わる短いコメントがあります。
`sys/ken/trap.c` の、不正命令のトラップを受ける箇所です。

> If illegal instructions are not being caught and the offending instruction is a SETD, the trap is ignored.
> This is because C produces a SETD at the beginning of every program which will trap on CPUs without 11/45 FPU.

訳すと次のようになります。

> 不正命令を捕まえていなくて、問題の命令が SETD なら、このトラップは無視する。
> C はすべてのプログラムの先頭に SETD を出し、それは 11/45 の FPU を持たない CPU ではトラップになるからだ。

このコメントは 3 つのことを言っています。

| 番号 | コメントが言っていること |
| --- | --- |
| 1 | C はすべてのプログラムの先頭に SETD を出す |
| 2 | FPU のない CPU では、SETD はトラップになる |
| 3 | 不正命令を捕まえていなければ、カーネルはそのトラップを無視する |

この記事では、Verilog で書いた PDP-11 の上で本物の Unix V6 を動かし、3 つを波形で 1 つずつ確かめます。
使うのは [09-PDP-11 / Unix V6](https://tommie-jp.github.io/soft-fpga/examples/09-pdp11/web) のデバッグパネルです。
この CPU コアには FPU がないので、コメントの言う「トラップになる CPU」に当たります。

---

## 1. 該当のコード

SETD は、浮動小数点演算装置 FP11 の命令です。命令語は 170011 で、以後の演算を倍精度で行うよう FP11 に指示します。
C の浮動小数点演算は倍精度で行うので、C のプログラムは動き出す前にこの設定を済ませます。

SETD を置いているのは、C のプログラムの入口 `crt0.s` です。`cc` はどのプログラムにも、この入口を先頭にリンクします。

```asm
start:
        setd
        mov     sp,r0
        mov     (r0),-(sp)
        tst     (r0)+
        mov     r0,2(sp)
        jsr     pc,_main
```

`setd` は 0 番地に置かれます。`main` が浮動小数点を使うかどうかに関係なく、最初に実行される命令です。

受ける側は、カーネルの `trap()` です。

```c
#define SETD    0170011         /* SETD instruction */
        ...
        case 1+USER: /* illegal instruction */
                if(fuiword(pc-2) == SETD && u.u_signal[SIGINS] == 0)
                        goto out;
                i = SIGINS;
                break;
        ...
        psignal(u.u_procp, i);

out:
        if(issig())
                psig();
        setpri(u.u_procp);
}
```

`pc` は、トラップが起きたときにハードウェアが積んだ戻り番地で、問題の命令の次を指しています。
`fuiword(pc-2)` は、ユーザー空間からその 1 語前、つまり問題の命令そのものを読みます。
それが SETD で、プロセスが不正命令のシグナル SIGINS を捕まえていなければ、`goto out` で `psignal` を飛ばします。
シグナルを送らないので、プロセスは何事もなかったように次の命令から続きます。

## 2. コマンドの先頭を数える

主張 1 は、ディスクの上のコマンドを調べれば確かめられます。
V6 の実行ファイルは 16 バイトのヘッダで始まり、その直後が 0 番地の命令です。

```text
# od /bin/ls
0000000 000410 010400 001050 002366 000000 000000 000000 000001
0000020 170011 010600 011046 005720 010066 000002 004767 000010
```

2 行目の先頭の 170011 が SETD です。`/bin`・`/usr/bin`・`/etc` の実行ファイル 112 個は、最初の命令で 3 つに分かれます。

| 最初の命令 | 個数 | 例 | 入口 |
| --- | --- | --- | --- |
| `setd`（170011） | 79 | `ls`・`sh`・`date`・`cc`・`ed` | `crt0.s` |
| `sys signal; 4; fptrap` の次に `setd` | 6 | `units`・`cdb`・`prof`・`sa`・`typo`・`ac` | `fcrt0.s`（6 章） |
| そのほか | 27 | `cat`・`as`・`mkdir`・`nroff` | アセンブラで書かれたコマンド |

C で書かれたコマンドは、すべて 1 行目か 2 行目に入ります。2 行目のコマンドは、3 語先の 6 番地に SETD を持っています。
3 行目のコマンドは、ソースが `cat.s` のようなアセンブラのファイルで、`crt0.s` をリンクしていません。
コメントの「every program」は、C で書かれたすべてのプログラムを指していました。

## 3. 観測の準備

[09-PDP-11 / Unix V6](https://tommie-jp.github.io/soft-fpga/examples/09-pdp11/web) を開き、`login:` に `root` で入ります。
`#` のプロンプトが出たら、次のボタンを押します。設定がまとめて入り、トリガーが待ち受けになります。

[▶ この設定を入れる](?scenario=setd-crt0)

そのあと、端末で `ls` を実行します。

ボタンは次の 3 つの操作をします。手で設定するときも、この順です。

1. **Logic Analyzer** のパネルを開く。
2. **Trigger** の Preset で `V6 crt0: SETD at user 0 (trap ignored)` を選び、**Set** を押す。
3. LA の信号を `VA`・`Data`・`WR`・`RD`・`PC`・`Mode`・`TRAP`・`SP` だけにする。

プリセットは、0 番地で命令語 170011 をフェッチした tick で発火します。
番地と命令語の両方を比べるので、止まるのは SETD で始まるプログラムの最初の命令だけです。
発火の後も 1600 サンプルを採ってから止まるので、トラップの始まりから終わりまでが 1 回の取り込みに入ります。

`ls` の代わりに `cat /etc/ttys` を実行しても、止まりません。`cat` の最初の命令は `mov (sp)+,r5`（012605）だからです。

## 4. トラップの入口

`ls` を実行すると、ファイルの一覧が出る前に止まります。LA の倍率を `1/2x` にすると、取り込んだ全体が見えます。

![SETD のトラップの全体。トリガーから 1477 tick の間、Mode が Kernel になる](docs/img/28-01-la-overview.png)

赤い点線がトリガーです。その左は、`exec` がプログラムを読み込んで、ユーザーモードへ戻るまでのカーネルの動きです。
トリガーの直後に `TRAP` が立ち、`Mode` はすぐ Kernel へ戻ります。次に User になるのは、右端に近い +1477 tick です。
`ls` は最初の 1 命令を実行しただけで、1477 tick をカーネルの中で過ごしました。

倍率を `16x` にして **⊙Trig** でトリガーの位置へ戻ると、入口の動きが読めます。

![トラップの入口。ベクタ 010 を読み、元の PS と PC をカーネルスタックに積む](docs/img/28-02-la-trap-entry.png)

トリガーからの tick 数で並べると、次のようになります。値は `tests/setd` の実行結果です。

| tick | 番地 | Mode | 起きたこと |
| --- | --- | --- | --- |
| 0 | 000000 | User | 命令語 170011 をフェッチ（トリガー） |
| +8 | 000010 | Kernel | ベクタの 1 語目 000320 を読む。新しい PC になる |
| +11 | 000012 | Kernel | ベクタの 2 語目 000341 を読む。新しい PS になる |
| +14 | 141776 | Kernel | 元の PS 170004 をカーネルスタックに積む |
| +17 | 141774 | Kernel | 元の PC 000002 をカーネルスタックに積む |
| +20 | 000320 | Kernel | `trap` の最初の命令をフェッチ |

CPU は 170011 を解読できず、予約命令のトラップを起こしました。主張 2 のとおりです。
ベクタは 010 番地で、カーネルの `low.s` に次のように書かれています。

```asm
/ trap vectors
        trap; br7+0.            / bus error
        trap; br7+1.            / illegal instruction
        trap; br7+2.            / bpt-trace trap
```

2 行目が 010 番地のベクタです。1 語目の `trap` は入口の番地 000320、2 語目の `br7+1.` が 000341 です。
`br7` は割り込み優先度 7 の PS（000340）で、下位に足した 1 がトラップの種類を表します。
入口のアセンブリはこの下位 5 ビットを取り出し、`trap()` の引数 `dev` に渡します。`case 1+USER` の 1 がこれです。

積まれた PC は 000002 です。SETD は 1 語の命令なので、戻り番地はその次を指しています。

## 5. SETD かどうかを確かめて、戻る

C の `trap()` に入るのは +248 tick です。それまでは、入口のアセンブリがレジスタを積んでいます。
倍率を `8x` にして +700 tick のあたりへ進むと、1 章の `if` の 1 行が波形に出ています。

![fuiword がユーザーの 0 番地を読み、170011 と比べ、u.u_signal を調べる](docs/img/28-03-la-setd-check.png)

| tick | 番地 | Mode | 起きたこと |
| --- | --- | --- | --- |
| +638 | 000000 | User | `fuiword(pc-2)` が 170011 を読む |
| +713 | 022000 | Kernel | `cmp r0,$170011` をフェッチ。SETD と一致する |
| +738 | 140352 | Kernel | `u.u_signal[SIGINS]` を読む。値は 000000 |
| +743 | 022012 | Kernel | `beq` をフェッチ。`out` へ飛ぶ |
| +749 | 021734 | Kernel | `out:` の `issig()` を呼ぶ |

+638 tick では、`Mode` が一瞬だけ User になります。
`fuiword` の中身は `mfpi (r1)` という命令で、カーネルモードのまま、割り込まれる前のモードの空間を読みます。
読んでいるのは、トリガーの tick にフェッチしたのと同じ、0 番地の語です。

`u.u_signal[SIGINS]` は 0 でした。`ls` は SIGINS を捕まえていないので、条件が 2 つとも成り立ちます。
`psignal` は呼ばれず、後始末の `issig()` と `setpri()` を通って、入口のアセンブリへ戻ります。

![rtt がカーネルスタックから PC と PS を取り出し、2 番地の命令をフェッチする](docs/img/28-04-la-return.png)

| tick | 番地 | Mode | 起きたこと |
| --- | --- | --- | --- |
| +1467 | 000522 | Kernel | `rtt` をフェッチ |
| +1472 | 141774 | Kernel | PC 000002 を取り出す |
| +1475 | 141776 | Kernel | PS 170004 を取り出す |
| +1478 | 000002 | User | `mov sp,r0`（010600）をフェッチ |

+14 tick と +17 tick に積んだ 2 語が、そのまま戻ってきました。ユーザーの SP は 177766 のままで、ユーザースタックには何も積まれていません。
プロセスから見ると、SETD は何もしない命令として 1 つ進んだだけです。主張 3 のとおりです。

その間に、カーネルは 131 個の命令を実行しました。次の `mov sp,r0` は 8 tick で終わります。
このシミュレータは 1 tick がおよそ 0.3 µs なので、1477 tick は約 0.4 ms です。
C で書かれたコマンドは、実行するたびに、最初の 1 命令でこれだけの時間を使っています。

## 6. 捕まえているプログラムでは無視されない

主張 3 には「不正命令を捕まえていなければ」という条件が付いています。この条件が要る理由は、もう 1 つの入口 `fcrt0.s` にあります。

```asm
/ C runtime startoff
/ with floating point interpreter

start:
        sys     signal; 4; fptrap
        setd
        mov     sp,r0
```

`cc -f` でコンパイルすると、`crt0.s` の代わりにこの入口がリンクされます。
`fptrap` は、FP11 の命令を 1 つずつソフトウェアで実行する模擬ルーチンです（`s3/fp1.s`）。
最初の `sys signal; 4; fptrap` で SIGINS のハンドラに登録しておき、FP11 の命令がトラップになるたびに呼んでもらいます。
FPU のない機械で浮動小数点を使うプログラムは、こうして動きます。

このとき SETD を無視すると、`fptrap` は倍精度への切り替えを知らないまま動くことになります。
そこでカーネルは、SIGINS を捕まえているプロセスには、SETD のトラップもそのまま届けます。

単位を換算する `units` が、この入口を使っています。次のボタンを押してから、端末で `units` を実行します。
3 章のボタンを押すと、この記事の画面は閉じます。上の文書の一覧から 28 章をもう一度開いて、ここへ戻ってください。
止まっていた `ls` は、ボタンを押したときに再開します。

[▶ この設定を入れる](?scenario=setd-fcrt0)

ボタンは **Stack / Memory** のパネルも開き、プリセット `V6 units: fptrap entry (SIGINS caught)` を待ち受けにします。
止まるのは、`fptrap` の最初の命令（007100 番地の `dec reenter`）をフェッチした tick です。

![fptrap の入口で止めたときの Stack / Memory パネル。SP の先頭 2 語が戻り番地と PS](docs/img/28-05-stack-fptrap.png)

右の列がユーザースタックです。SP は 177760 で、先頭の 2 語は 000010 と 170004 です。
SETD のトラップが起きる前の SP は 177764 でした。その下に 2 語が増えています。
左の Call chain は R5 をたどった物で、R5 が 0 のこの時点では意味を持ちません。

2 語を積んだのは、カーネルの `psig()` です。

```c
        if((p=u.u_signal[n]) != 0) {
                u.u_error = 0;
                if(n != SIGINS && n != SIGTRC)
                        u.u_signal[n] = 0;
                n = u.u_ar0[R6] - 4;
                grow(n);
                suword(n+2, u.u_ar0[RPS]);
                suword(n, u.u_ar0[R7]);
                u.u_ar0[R6] = n;
                u.u_ar0[RPS] =& ~TBIT;
                u.u_ar0[R7] = p;
                return;
        }
```

ユーザーの SP を 4 下げ、元の PS と PC を `suword` でユーザースタックに書き、戻り先の PC をハンドラの番地に書き換えます。
ハードウェアが割り込みで積むのと同じ 2 語を、カーネルがユーザースタックの上に作っています。
波形では、トリガーより前に次の動きが残っています。割り込みが入らなかった回の値です。

| tick | 番地 | Mode | 起きたこと |
| --- | --- | --- | --- |
| -3008 | 000006 | User | 命令語 170011 をフェッチ |
| -2370 | 000006 | User | `fuiword(pc-2)` が 170011 を読む |
| -2270 | 140352 | Kernel | `u.u_signal[SIGINS]` を読む。値は 007100 |
| -2203 | 022644 | Kernel | `psignal(u.u_procp, SIGINS)` に入る |
| -1636 | 023144 | Kernel | `psig()` に入る |
| -989 | 177762 | User | 元の PS 170004 をユーザースタックに書く |
| -743 | 177760 | User | 元の PC 000010 をユーザースタックに書く |
| -596 | 141774 | Kernel | カーネルスタックの戻り先を 007100 に書き換える |
| -11 | 000522 | Kernel | `rtt` をフェッチ |
| 0 | 007100 | User | `fptrap` の `dec reenter` をフェッチ（トリガー） |

5 章と違うのは -2270 tick です。`u.u_signal[SIGINS]` に `fptrap` の番地 007100 が入っていて、条件の後半が成り立ちません。
`rtt` が取り出す PC は、-596 tick に書き換えられた 007100 です。戻った先は SETD の次ではなく、ハンドラになりました。

**▶ Step** を 2 回押すと 600 tick 進み、`fptrap` の終わりまでが波形に入ります。

![fptrap の出口。rti がユーザースタックから PC と PS を取り出し、10 番地へ戻る](docs/img/28-06-la-fptrap-rti.png)

| tick | 番地 | 起きたこと |
| --- | --- | --- |
| +26 | 177760 | 戻り番地 000010 を取り出して控える |
| +176 | 000006 | 戻り番地の 1 語前から、止まった命令 170011 を読む |
| +327 | 007502 | `i.setd` の `bis $m.ext,fpsr` をフェッチ。倍精度の印を立てる |
| +509 | 007636 | `rti` をフェッチ |
| +514 | 177760 | PC 000010 を取り出す |
| +517 | 177762 | PS 170004 を取り出す |
| +520 | 000010 | `mov sp,r0`（010600）をフェッチ |

`fptrap` は、カーネルと同じやり方で止まった命令を調べます。戻り番地の 1 語前を読み、命令語の下位で分岐します。
SETD の処理は、模擬ルーチンが持つ状態語 `fpsr` に倍精度の印を立てる 1 命令です。
最後の `rti` はユーザーモードで実行され、`psig()` が積んだ 2 語を取り出して 10 番地へ戻ります。

`fptrap` の中で動いたのは 47 命令、520 tick です。SETD のフェッチから数えると 3528 tick かかりました。
`psig()` は、SIGINS のハンドラだけは呼んだ後も登録を消しません（上のコードの `n != SIGINS`）。
`units` が実行する FP11 の命令は、1 つ残らずこの経路を通ります。

## 7. V7 でも変わらなかった

Version 7 の `trap.c` には、同じコメントと同じ判定が残っています（[trap.c](https://github.com/dspinellis/unix-history-repo/blob/Research-V7/usr/sys/sys/trap.c)）。

```c
        case 1+USER: /* illegal instruction */
                if(fuiword((caddr_t)(pc-1)) == SETD && u.u_signal[SIGINS] == 0)
                        goto out;
                i = SIGINS;
                break;
```

V7 の `crt0.s` も `setd` で始まり、`fcrt0.s` も `sys signal; 4; fptrap` の次に `setd` を置いています（[csu](https://github.com/dspinellis/unix-history-repo/tree/Research-V7/usr/src/libc/csu)）。
27 章の `swtch()` は V7 で作り直されましたが、こちらは手を入れられませんでした。

この作りでは、FPU のある機械でもない機械でも、同じ `ls` がそのまま動きます。
その代わりに、FPU のない機械は C のコマンドを実行するたびに 1 回、無視するだけのトラップを通ります。

## 8. 確かめた結果

| コメントが言っていること | 確かめたこと |
| --- | --- |
| C はすべてのプログラムの先頭に SETD を出す | 実行ファイル 112 個のうち、C で書かれた 85 個が入口に SETD を持つ。79 個は 0 番地、6 個は 6 番地。アセンブラの 27 個は SETD で始まらない |
| FPU のない CPU では、SETD はトラップになる | 170011 のフェッチから 8 tick でベクタ 010 を読み、`trap` へ入った |
| 捕まえていなければ、トラップを無視する | `ls` では `u.u_signal[SIGINS]` が 0 で、`psignal` を通らずに 2 番地へ戻った。1477 tick、131 命令 |
| 捕まえていれば、無視しない | `units` では `psig()` がユーザースタックに 2 語を積み、`fptrap` が SETD を処理して `rti` で 10 番地へ戻った |

SETD でない不正命令は、どちらの条件にも当たらず SIGINS になります。捕まえていなければ、プロセスは core を残して終わります。
[63 章](?doc=63-mknod-Illegal-instruction-調査.md) に、その実例があります。
