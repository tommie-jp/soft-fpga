# 14. cc コンパイル失敗 — バグ調査記録 <a class="qr-link" href="../../../docs/09-PDP11/41-QR.png">QR</a>

## 1. 症状

```text
# cc hello.c
Bus error -- Core dumped

# /lib/c0 hello.c /tmp/tmpa /tmp/tmpb
/lib/c0: too large
```

`cc` を実行すると Bus error でクラッシュ。コンパイラパス `/lib/c0` を直接呼ぶと
「too large」（exec ENOMEM）が返る。`hello.c` は構文的に正しい 5 行のプログラム。

## 2. 診断過程

### 2.1 コンパイラパスの存在確認

```text
# ls /lib/c0 /lib/c1 /lib/c2 /lib/cpp
/bin/cpp not found
/lib/c0  /lib/c1  /lib/c2  ← 存在する
```

`/lib/cpp`（C プリプロセッサ）が存在しない。`cc` が cpp を exec しようとして
Bus error になった可能性を疑ったが、後の調査で本質ではないと判明。

### 2.2 バイナリサイズ確認

```text
# size /lib/c0
12608+2728+7190=22526 (53776)
```

text+data+bss = 22526 バイト = 352 clicks（1 click = 64 バイト）。
Unix V6 の exec チェック `text+data+SSIZE > maxmem` で SSIZE ≈ 20 とすると、
失敗するには `maxmem < 372 clicks = 23.8 KB` でなければならない。

### 2.3 SIMH との比較（決定的）

同一ディスクイメージ (`unix_v6_rk05.dsk`) を SIMH で実行:

```text
sim> set cpu 11/40
sim> attach rk0 examples/09-pdp11/disk/unix_v6_rk05.dsk
sim> boot rk0
@rkunix
login: root
# cc hello.c
# a.out
Hello, World!
```

**SIMH では正常動作** → ディスクイメージは正常、soft-FPGA シミュレーター固有のバグ。

### 2.4 ブート時 `mem=` 表示なし

Unix V6 カーネルはブート時にメモリ量を `printf("mem = %d\n", maxmem)` で表示するが、
soft-FPGA では表示されない。SIMH でも同様に表示されない（このカーネルバイナリに
その出力は含まれない）。

### 2.5 カーネルソース確認

```text
# ls /usr/sys/ken
alloc.c clock.c fio.c iget.c main.c malloc.c nami.c pipe.c prf.c
rdwri.c sig.c slp.c subr.c sys1.c sys2.c sys3.c sys4.c sysent.c
text.c trap.c
```

```text
# ls /usr/sys/conf
data.s m40.s m45.s mkconf.c sysfix sysfix.c
```

- `l.s`（リンカスクリプト）は空
- `data.s` はほぼ空（`.data` ディレクティブのみ）
- `maxmem` はコンパイル時定数ではなく、`main.c` 内で動的検出

## 3. 根本原因（仮説）

### 3.1 I/O ページ ノーウェイト + PAR 同期書き込みの競合

`bus.v`:

```verilog
assign waiting = ram_access && ~ram_done;  // I/O 時は ram_access=0 → waiting=0
assign bus_ack  = grant_cpu && !waiting;    // I/O アクセスは即 ACK
```

I/O ページ（UISA/KISA レジスタを含む）へのアクセスはウェイトサイクルなし。
CPU は I/O 書き込みの直後に次のバスサイクルを開始できる。

`mmu.v`:

```verilog
always @(posedge clk)
  if (pxr_wr)
    par_h[pxr_addr_5_0] <= pxr_data_in[15:8];  // 非ブロッキング代入
    par_l[pxr_addr_5_0] <= pxr_data_in[7:0];
```

PAR（ページアドレスレジスタ）書き込みは `<=`（非ブロッキング）。
同一 posedge で CPU が次のメモリアクセスを開始した場合、
PAR の新しい値は次の評価サイクルまで反映されない。

### 3.2 物理メモリプローブへの影響

Unix V6 `main.c` はブート時に物理メモリをプローブして `maxmem` を決定する。
プローブはページレジスタを更新しながら順次物理アドレスを探索する。

```text
1. UISA6（ユーザー I-space PAR6）に物理クリック N をセット
2. `mfpi` 命令でユーザー仮想 0o140000 を通じてアクセス
3. バスエラーが出なければ maxmem++
4. バスエラーなら探索終了
```

ステップ 1 の I/O 書き込みが即 ACK → CPU が次の命令へ進む。
ステップ 2 の `mfpi` 実行時に UISA6 がまだ旧値 → 誤ったアドレスを参照。
プローブが早期終了し、`maxmem` が実際より遥かに小さな値に設定される。

### 3.3 PAR アドレス整合性（確認済み・問題なし）

PAR 書き込みインデックスと MMU 変換インデックスの整合性を確認:

- `pxr_addr_5_0 = pxr_addr[5:0]`（書き込み側）
- `pxr_index = {cpu_cm, enable_d_space ? ~cpu_i_access : 1'b0, cpu_apf}`（読み出し側）

KISA6 書き込み時: `pxr_addr_5_0 = 6`、カーネルページ 6 変換時: `pxr_index = 6`。
インデックスは一致しており、アドレス計算のバグではない。

## 4. 修正候補

### 案 A: I/O 書き込み後に 1 クロックウェイト追加（推奨）

`bus.v` の `waiting` に I/O 書き込みウェイトを追加:

```verilog
reg iopage_wr_wait;
always @(posedge clk)
  iopage_wr_wait <= iopage_wr;  // 1 クロック遅延フラグ

assign waiting = (ram_access && ~ram_done) || iopage_wr_wait;
```

これにより PAR 書き込み直後に CPU が停止し、非ブロッキング代入が確定してから
次のアクセスが始まる。

### 案 B: mmu.v PAR 書き込みをブロッキング代入に変更（リスク大）

`<=` を `=` に変更すれば即時反映されるが、
他の組み合わせ論理との競合が生じる可能性がある。Verilog の設計原則に反するため非推奨。

### 案 C: 既知バグとして記録し cc をデモから除外

修正を保留し、デモシナリオから `cc` を削除。
`dc`・`ed`・`sh` など動作確認済みの機能でデモを構成する。

## 5. デモへの影響

`cc` 以外の機能はすべて正常:

| 機能 | 状態 |
|------|------|
| ブート・ログイン | 正常 |
| sh・ls・cat・ed・dc | 正常 |
| Logic Analyzer | 正常 |
| GPR / MMU パネル | 正常 |
| RK11 ディスク波形 | 正常 |
| cc / c0 / c1 / c2 | **失敗**（maxmem 不足） |

## 7. 追加調査（2026-06-04）— 信号トレースによる根本原因の特定

### 7.1 結論サマリ

3 節の「PAR 同期書き込み競合（案A）」仮説は**誤り**だった。信号トレースで実測した
真の原因は以下の連鎖:

1. **メモリプローブが過大検出** — V6 `main.c` のプローブが実 RAM ではなく
   22bit ほぼ全空間（~4MB / UISA0 click=0o177774）を「実装メモリ」と誤検出する。
2. **過大な maxmem によりプロセスが物理メモリ最上位に配置** — `cc` のコンパイラパス
   `/lib/c0` の expand-down スタックの PAR が `0o177600`（= top − 0o200, top≈4MB）になり、
   ユーザ仮想 `0170440` が物理 `0o17770440`（I/O ページ域）にマップされる。
3. **I/O ページ域アクセスでバスエラー** → cc が `Bus error -- Core dumped`、
   その後 EMT/TRAP ベクタ（pc=000030/000036）で無限トラップループ。

### 7.2 過大検出のメカニズム（実測）

- プローブは `UISA0`（ユーザ I-space PAR0, 物理 `0o17777640`）に click 番号を
  単調増加で書き、`mfpi` でユーザ仮想 0 を読んでフォルトの有無で実装メモリ末尾を判定する。
- RTL では `ram_async` が `ram_addr[17:0]`（18bit）でアクセスされ、範囲外アドレスが
  エイリアスして**有効データを返す**。さらに範囲外を検出する `ram_bus_error` は
  **`mfpi` 命令の読み取り（istate s4）で CPU をトラップさせない**（`iopage` の
  `no_decode` 経由 `iopage_bus_error` は cc アクセスで正しくトラップする）。
- このため `fuibyte` がフォルトを検知できず、プローブが末尾検出に失敗して全空間を歩く。

### 7.3 確認できた事実

- **SIMH（`set cpu 11/40` + `256k`）では `cc hello.c` が正常動作** → ディスク/カーネルは
  正常。cpus-pdp11 RTL 固有。
- **MMU は既に 18bit モード**（`mmu.v: assign map22 = 1'b0;`）。「11/40 / 18bit に寄せる」
  対策は MMU アドレッシングの面では既に成立している。残る差分は上記プローブ挙動。
- `mem = NNN` がブート時に出ないのは別件で、SIMH でも同様（このカーネルは出力しない）。

### 7.4 発見した派生バグ（MMU page length error）

`mmu.v` の書き込み経路 `acf=6`（read/write）で、ページ長エラー（expand-down スタックの
valid 範囲外アクセス）が `signal_trap`（遅延トラップ）になっている。PDP-11 仕様では
ページ長エラーは**常に abort**（read 経路は正しく `signal_abort`）。これだとアクセスが
完了してしまうため、`signal_abort` に修正すべき。

### 7.5 候補修正（[cc-fix-candidates/](cc-fix-candidates/)）

- `bus-probe-detection-fix.patch` — 22bit デコード化 + 実 RAM(248KB) を超える
  「存在しないメモリ」を `iopage` の no_decode 経路（確実にトラップ）に通す。
  → プローブの UISA0 スイープは 248KB で停止するようになる。
- `mmu-pagelen-abort-fix.patch` — 7.4 のページ長エラー abort 修正。

**ただし両方適用しても `cc` はまだ通らない**: プローブのスイープは 248KB で止まるのに、
プロセス配置（スタック PAR）が依然 4MB 相当（`0o177600`）を指す不整合が残る。
`maxmem` 設定とプロセス物理配置の間に、未解明の経路がもう一段ある。

### 7.6 残る作業（完全修正に必要）

- CPU の `mfpi`/`mtpi` 実行中（istate s4）の `bus_error` 取りこぼしを波形レベルで特定し、
  範囲外メモリ読み取りが確実にトラップ（`fuibyte` が -1 を返す）するようにする。
- もしくは `ram_async` 側で範囲外（実装 RAM 超）アクセスを明示的にバスエラー化する。
- プローブが正しい maxmem を設定したうえで、プロセス配置のスタック PAR が RAM 内に
  収まることを `UISA7` トレースで確認する。

## 8. オプション2 実装（2026-06-04）— メモリ検知の修正

### 8.1 実装内容（[bus.v](../../../../vendor/cpus-pdp11/rtl/bus.v)）

実装 RAM 上限を **192KB（0o600000）** とし、それ以上 ～ I/O ページ未満を
「存在しないメモリ（nxm）」として扱う。nxm アクセスは `ram_access=0` かつ
`iopage_access=0`（→ `bus_data_out=0xffff`）にしつつ `bus_error=1` を立てる。
これは iopage no_decode と全く同じ条件で、**確実に CPU をトラップさせる**
（デバイスデコードには当てないので副作用なし）。`ram_present` も 0o600000 に整合。

併せて [mmu.v](../../../../vendor/cpus-pdp11/rtl/mmu.v) の write 経路 page-length error を
`signal_abort` に修正（7.4 参照）。

### 8.2 結果

- **メモリプローブの過大検出を解消**: probe の UISA0 スイープが従来の 4MB
  （click=0o177774）から **192KB（click=0o6000）で正しく停止**するようになった（実測）。
  → ユーザ指摘の「ブート時のメモリ検知が正しくない」を直接修正。
- **ブート・login は正常**（デモに影響なし）。

### 8.3 残課題 — cc はまだ失敗（別バグ）

> **注（後日解決）**: 本節は調査途中の状態。この「別バグ」は §9 で根本原因（トラップ
> 優先度 trap_bus > trap_abort）を特定し**解決済み**。cc はネイティブ・ブラウザ両方で
> 正常動作する（§9・§10 参照）。

メモリ検知を正したにもかかわらず `cc h.c` は依然 `Bus error`（pc=002644,
ユーザ仮想 `0170440` → 物理 `0o17770440` = I/O ページ, cm=3 ユーザモード）。
この物理アドレスは **メモリ構成（56KB/192KB/248KB/22bit/MMU修正）に依らず完全に一定**。

トレースで判明: cc プロセスの実行中、**ユーザ PAR7（UISA7=iopage offset 0o7656 /
UDSA7=0o7676）への書き込みが全期間で 0 回**。つまりセグメント7（スタック）の PAR が
cc プロセス用に設定されないまま参照され、I/O ページにマップされている。

→ メモリ検知とは独立した、**exec/コンテキスト切替時のユーザ PAR セットアップ**の
問題と推定。次はこの PAR7 がどこで設定される（はずな）のか、`sureg`/`estabur` 相当の
バスサイクルと、`mfpi`/`mtpi`（前モード空間アクセス）時の PAR 選択を追う必要がある。

## 9. 解決（2026-06-04）— cc コンパイル成功 🎉

### 9.1 最終的な根本原因

`cc` 失敗は **2 つの独立した RTL バグ**の合わせ技だった:

1. **メモリプローブの過大検出**（8 節）— プロセスがメモリ最上位に配置され不安定。
2. **トラップ優先度の誤り（決定打）** — V6 のユーザスタックは expand-down セグメント。
   c0 等がスタックを下方に伸ばすと **ページ長 abort（MMU abort, vector 0o250）**が発生し、
   V6 はこれを受けてスタックを自動拡張するはず。ところがこの CPU は abort 中のアクセスも
   バスへ出してしまい、expand-down の範囲外ブロックが I/O ページ物理に変換されて
   **spurious な bus error（vector 4）**も同時にラッチされる。`pdp11.v` のトラップ優先度が
   **bus error > MMU abort** だったため、V6 は致命的バスエラー扱いにし
   `Bus error -- Core dumped` で落ちていた。PDP-11 仕様では MMU abort が最優先
   （メモリサイクルを抑止する）。

### 9.2 修正（vendor/cpus-pdp11）

| ファイル | 修正 | 役割 |
|----------|------|------|
| `rtl/pdp11.v` | トラップ優先度を **`trap_abort`（vector 0o250）> `trap_bus`（vector 4）** に変更 | **決定打**。スタック自動拡張の abort を bus error より優先 |
| `rtl/pdp11.v` | `assert_trap_bus = bus_error & ~mmu_abort` | abort 時の spurious bus error を抑止（防御的） |
| `rtl/pdp11.v` | デバッグ用 `$display("BUSERR...")` を削除 | 正常動作のスタック拡張で多発するノイズを除去 |
| `rtl/mmu.v` | write 経路 acf=6 のページ長エラーを `signal_abort`（read 経路と一致、PDP-11 仕様） | ページ長 abort を正しく発火 |
| `rtl/bus.v` | 実装 RAM=192KB + 範囲外を iopage no_decode 経路へ（8 節） | メモリ過大検出を解消 |

### 9.3 検証結果

```text
# cc t.c
# a.out
VERIFY-121          ← printf("...%d", 11*11) が実行時計算して出力
```

- `write(2)` ベース・`printf`/libc ベースの両方で **cc コンパイル＆実行成功**。
- `ls`・`cat`・`sh` 等の基本コマンド、ブート・login も正常（リグレッションなし）。
- メモリプローブは 192KB で正しく停止（過大検出解消）。

### 9.4 注意

- 大量のテスト実行で `/tmp` に `ctm*` 一時ファイルが溜まると `cc` が
  `No relocation bits` / `Bad system call` で失敗する（fs 劣化）。
  その場合は V6 内で `rm -f /tmp/*; sync` で回復する。

## 10. WASM/ブラウザ検証（2026-06-05）

`scripts/build-wasm-09.sh` で WASM を再ビルド（cc 修正済み RTL を反映、`web/sim.js`・
`web/sim.wasm` 更新）。クリーン化したディスクを `web/disk/` に配置。Playwright で実ブラウザ検証:

- ✅ ブラウザでブート → `login:` 到達（全ブート段階 done）。
- ✅ `root` ログイン → `cc c.c` が **バスエラーなしで完了**（元の不具合は解消、ネイティブと一致）。
- ✅ **コンパイルした a.out もブラウザで正常実行**（クリーンな手順で再検証）:
  - `write(2)` 版（356 バイト, 1 ブロック）→ `OK7` を出力。
  - `printf`/libc 版（**1188 バイト, マルチブロック**）→ `PF-45`（=5×9）を出力。
    `od a.out` で先頭ワード `000407`（V6 a.out マジック）・`size` もヘッダと一致した正常な実行ファイル。

### 10.1 当初の `a.out` "syntax error" について（誤検出だった）

最初のブラウザ検証で `a.out` が `syntax error` になったのは、**WASM/cc の実バグではなく、
テスト駆動側のアーティファクト**だった。原因は、キー入力を `worker.postMessage` で
一気に送ったため UART RX が取りこぼし・重複し（"cat"→"ctt" 等の文字化け）、
さらに化けた入力がログアウトを誘発して stale/壊れたファイルが残ったこと。

→ **1 文字ずつ実時間でペーシング（~90ms/char）して送る**クリーンな手順では、
  `write` 版・`printf`/libc 版（マルチブロック a.out）ともにコンパイル＆実行が完全に正常。
  ブラウザ（WASM/MEMFS）のディスク読み書きにも問題はなかった。

→ 結論: ユーザ報告の cc バスエラーは **ネイティブ・ブラウザ両方で完全に解消**。
  ブラウザでもコンパイルした実行ファイルが正しく動作する（残課題なし）。
