**アーキテクチャ**: 式文字列 → `_trigParse`（UI）→ `trigCompileToWasm`（UI）→ `postMessage` → Worker 内で `new WebAssembly.Instance` → simLoop 毎フレームに全新着サンプルを Wasm ネイティブ評価（≈ 2–5 ns/sample）。Expr Set 時に `ring_tick_mask=0`（毎 tick サンプリング）へ自動切り替え。

**信号対応状況**:

| 比較種別 | 対応信号 | 非対応 |
|---------|---------|-------|
| 数値比較 `== != < > <= >=` | 全信号（VA, PC, RD, Mode, istate, ISN, PSW, R0-R5 等） | Cycle（仮想信号） |
| 文字列比較 | `Mode == "USER"/"KERNEL"/"SUPER"`, `istate == "F1"/"C1"` など | `ISN == "MOV …"`, `PSW == "…"`, `Cycle == "FETCH"` |
| エッジ検出 `.rising/.falling/.edge` | 全非仮想信号 | Cycle（仮想信号） |

**Cycle / ISN 文字列 / PSW 文字列の代替式**:

| やりたいこと | 代替式 |
|------------|-------|
| `Cycle == "FETCH"` | `RD.rising && istate == "F1"` |
| `Cycle == "MEM_RD"` | `RD == 1 && istate != "F1"` |
| `ISN == "CLR R1"` | `ISN == 0o5001` |
| `PSW` フラグ確認 | `PSW == 0o0340`（数値） |

**残課題**: Cycle（仮想信号）・ISN 文字列・PSW 文字列に対して Worker 内 JS フォールバック（`importScripts` + `_trigEvalExpr`）を追加すれば完全対応できる。現状はコンパイルエラーを表示して代替式を案内している。

### 7. V6 ディスクイメージのコマンド動作不良（2026-06-11 調査）

MCP Playwright で実機テストを実施。以下のコマンドが exec 失敗する。

#### 実行不可コマンド一覧

| コマンド | 場所 | 失敗様式 | 判明した原因 |
|---------|------|---------|------------|

| `bc` | `/usr/bin/bc` | `bc: not found` | exec 失敗（原因未特定） |
| `chess` | `/usr/games/chess` | `not found` | exec 失敗（16088B, pure executable 形式）|
| `ttt` | `/usr/games/ttt` | `not found` | exec 失敗（2192B, executable 形式）|
| `wump` | `/usr/games/wump` | `not found` | exec 失敗（5184B, large file）|

#### 動作確認済みコマンド（同テストで確認）

| コマンド | 結果 |
|---------|------|
| `/bin/bas` | ✓ BASIC インタプリタ起動 |
| `/usr/games/bj` | ✓ BlackJack 正常動作 |
| `/usr/games/moo` | ✓ MOO（数当てゲーム）正常動作 |
| `/usr/games/cubic` | ✓ cubic 起動確認 |

`/bin/cdb` は「`a.out not found`」と報告することがあるが（a.out 不在時）、
a.out を用意して `cdb a.out` を実行すると `Trace/BPT trap -- Core dumped` でクラッシュする。

#### 未解明点

- `dc` は magic 破損で確定。`bc`・`chess`・`ttt`・`wump` の失敗原因は未特定。
- `ttt`（0407 形式, 2192B）と `cubic`（0407 形式, 2468B）が同フォーマット・同サイズ帯で動作が分かれる。
- 仮説: 使用するシステムコールや命令セット（FPU 等）の差異か、特定アドレスへの依存の可能性。

詳細: [10-unix-v6-コマンドリファレンス §7](?doc=10-unix-v6-コマンドリファレンス.md)、[06-unix-v6-demo-commands.md](?doc=06-unix-v6-demo-commands.md)

#### 追記（2026-11-22）: 空きリストに同じブロックが重複している

28 章の準備で `cc` を使ったとき、作った `a.out` が `Illegal instruction` で落ちた。原因はディスクイメージの空きリストだった。

- 配布ディスクのスーパーブロックの空きリストに、同じブロック番号が重複して入っている。先頭付近は
  `134 2979 119 2974 134 2423 2527 3030 3030 2527 …` で、全体では 11 個のブロックが 2〜4 回現れる（3030 は 3 回）。
- `alloc()` は同じブロックを 2 回渡すので、数ブロックのファイルを作ると、ファイルの中の 2 か所が同じブロックを指す。
  例: 1704 バイトの `a.out` の inode が `[2979, 2423, 3030, 3030]` になり、3 ブロック目の中身が 4 ブロック目で上書きされた。
- 重複は `ps` のパッチを当てる前の写し（`unix_v6_rk05.dsk.pre-psfix.bak`）にもある。配布元のイメージの時点で入っていた。
- 起動直後の `icheck /dev/rk0` も、`bad`（範囲外のブロック番号）と `dup` を多数報告する。
- 壊れたファイルを消すと、重複したブロックが 2 回 `free()` され、空きリストの重複は残り続ける。

上の表の「バイナリ破損」や [63 章](?doc=63-mknod-Illegal-instruction-調査.md) の `/etc/mknod` の欠損は、これで説明がつく見込み（未検証）。
小さいファイル（27 章の `swp.c` の `a.out` など）は、たまたま重複に当たらずに動く。

対処（2026-11-22 済み）: [`scripts/patch-v6-disk-freelist.py`](../../scripts/patch-v6-disk-freelist.py) が、ホスト側で全 inode の使用ブロックを数え直し、空きリストを作り直す。
`scripts/build-wasm-09.sh` が `ps` のパッチの後に自動で当てる。公開用とテスト用の 2 つのディスクに適用した。

| 項目 | 作り直す前 | 作り直した後 |
| --- | --- | --- |
| 空きリストに 2 回以上あるブロック | 11 個 | 0 個 |
| ファイルが使用中なのに空きリストにあるブロック | 19 個 | 0 個 |
| どこにも属さないブロック | 272 個 | 0 個 |
| 空きブロック（`icheck` の `free`） | 1064 | 1301 |
| `cc` で数ブロックの `a.out` を作る | アセンブラが `x 0089` を出して失敗 | 通る |

作り直した後も `icheck /dev/rk0` は `29 dups in free` と表示する。これは `icheck` がファイル同士の重複と空きリストの重複を
同じ変数（`ndup`）で数えているためで、29 個はすべてファイル同士の重複である。

既に壊れているファイルは、これでは直らない。分かっているものは次のとおり。

- `/bin/dc`（inode 10）と `/usr/fort/fc1`（inode 401）: 間接ブロックが別の内容で上書きされている。
- `/usr/sys/ken/sys1.c`（inode 51）: 間接ブロックが 0 で埋まっていて、中身を読めない。
- `/usr/sys/ken/main.c` と `/usr/sys/dmr/bio.c`: それぞれ 1 ブロックが別の内容になっている。

カーネルのソースを記事に引用するときは、傷みのない写し（[unix-history-repo](https://github.com/dspinellis/unix-history-repo) の `Research-V6` ブランチ）と照らし合わせる。

テスト用の `examples/09-pdp11/disk/unix_v6_rk05.dsk` は公開用の `web/disk/` と中身が違う（ファイルが 1 つ多い）。
作り直した後は、どちらも空きブロックを番号の小さい順に渡す。
