## 1. Overview

In bare-metal mode, a Python assembler writes each instruction directly into RAM, and a PC trigger detects the instruction fetch to capture a Logic Analyzer trace. Because Unix V6 is not booted and only the target instruction is executed, pure instruction cycles can be observed without interference from OS interrupts or device accesses.

> **EIS instructions (Phase N) extended to 61 cases (2026-06-06)**
>
> 6 cases for `MUL`, `DIV`, `ASH`, and `ASHC` were added. At zoom=8, the
> multi-cycle waits of internal hardware (`mul1616` ~16 clk, `div3216` ~32 clk) are made visible.

## 2. Timing Diagram Layout

### 2.1 T Axis and Trigger Marker

```text
T: -20 -19 … -2 -1 | 0 | +1 +2 … +14
                    ↑
                  TRIG (red dashed line)
```

| Symbol | Meaning |
|--------|---------|
| **T = 0** | Trigger fire point = start of the opcode fetch for the instruction under observation (clock 1) |
| **T < 0** | Pre-trigger period. The **setup instructions** executed just before (register initialization, etc.) are visible |
| **T > 0** | Instruction execution phase (decode, operand fetch, ALU, writeback) |

> **Trigger condition at T = 0**: `bus_rd=1` and `VA == trigger_pc`.
> Fires only when the very first bus cycle of an instruction fetch matches.

### 2.2 Cycle Decode Lane (Color Band at the Top)

The **Cycle** band at the top of the waveform automatically classifies and color-codes each bus cycle.

| Color | Type | Detection Condition |
|-------|------|---------------------|
| Blue | **FETCH** | `bus_rd=1` and `VA == PC` (instruction fetch) |
| Green | **MEM\_RD** | `bus_rd=1` and `VA ≠ PC` (data read) |
| Red | **MEM\_WR** | `bus_wr=1` (data write) |
| Light green | **IO\_RD** | Read from I/O page (`0o760000–0o777777`) |
| Orange | **IO\_WR** | Write to I/O page |
| Orange | **TRAP** | Trap occurred flag |

Periods with no color band = bus inactive (CPU internal processing only).

### 2.3 ISN Row (Instruction Disassembly)

The 16-bit opcode captured at samples where istate is **f1 (fetch)** is converted to a
**simplified mnemonic** for display. Immediate and index words are shown with the actual
values read from the bus waveform (or `#imm` / `X(Rn)` placeholders if unavailable).

```text
ISN: MOV #1200,R1   →   CLR R2   →   MOVB (R1),R2   →   BR .-5
```

The transition "setup instruction → observed instruction → loop branch" can be read directly.

### 2.4 Relationship Between PhysAddr, VA, and PC

```text
PC       = "next instruction address" after +2 was applied immediately following the fetch
PhysAddr = physical address on the bus (18-bit, after MMU translation)
VA       = virtual address issued by the CPU (16-bit, before MMU translation)
```

During an instruction fetch cycle, **`VA == PC - 2`** (the address being fetched).
PhysAddr is the value produced by the MMU translating VA. In kernel mode with paging enabled, VA = PhysAddr.

> Even during clocks when the bus is inactive, PhysAddr retains its previous value (latch behavior).

### 2.5 Signal List

| Signal | Description |
|--------|-------------|
| `PhysAddr` | Unibus physical address (= `PC - 2` during instruction fetch) |
| `VA` | Virtual address (shown only for memory-access cases) |
| `Data` | Bus data (read value for RD, written value for WR) |
| `RD` / `WR` | Bus read / write strobe |
| `BYTE` | Byte operation flag (High only for byte instruction cases) |
| `PC` | Program counter (next instruction address, updated immediately after fetch) |
| `PSW` | Processor Status Word (format: `CM PM P# TNZVC`) |
| `Mode` | Current CPU mode (`Kernel` / `User`) |
| `istate` | CPU microsequencer state (symbolic display: f1/c1/d\*/s\*/e1/w1, etc.) |
| `ISN` | Current instruction opcode (disassembled display) |
| `R0`–`R5`, `SP` | General-purpose registers (octal display) |
| `M1(addr)` | Memory probe value (RAM contents at the specified address recorded every sample) |

## 3. istate Sequence and Instruction Phases

For the full definition of istate (CPU microsequencer), see [57 Registers & istate](?doc=57-レジスタとistate.md).
The key points needed to read timing diagrams are shown below.

| istate | Phase | Description |
|--------|-------|-------------|
| **f1** | Fetch | `isn ← M[PC]`, `PC ← PC + 2` |
| **c1** | Decode | Analyze instruction type and operand fields |
| **s1–s4** | Source | Source operand effective address calculation and bus read |
| **d1–d4** | Destination | Destination effective address calculation and bus read (for read-modify-write instructions) |
| **e1** | Execute | ALU operation, PSW update, PC/SP adjustment |
| **w1** | Writeback | Write result back to register / memory |

### T Count Quick Reference

| Instruction Category | Typical istate Sequence | Cycles | Bus Accesses |
|---------------------|------------------------|--------|--------------|
| Single-operand register (CLR, COM, INC…) | f1→c1→d1→e1→w1 | **5T** | FETCH ×1 |
| Double-operand register-register (MOV R0,R1) | f1→c1→s1→d1→e1→w1 | **6T** | FETCH ×1 |
| Immediate (MOV #n,R1) | f1→c1→s1→s4→d1→e1→w1 | **7T** | FETCH ×2 |
| Register indirect read (MOV (R1),R2) | f1→c1→s1→s4→d1→e1→w1 | **7T** | FETCH+MEM\_RD |
| Register indirect write (MOV R1,(R2)) | f1→c1→s1→d1→d4→e1→w1 | **7T** | FETCH+MEM\_WR |
| Auto-increment (MOV (R1)+,R2) | f1→c1→s1→s2→s4→d1→e1→w1 | **8T** | FETCH+MEM\_RD |
| Auto-decrement (MOV -(R1),R2) | f1→c1→s1→s4→d1→e1→w1 | **7T** | FETCH+MEM\_RD |
| Indexed (MOV X(R1),R2) | f1→c1→s1→s2→s4→d1→e1→w1 | **8T** | FETCH×2+MEM\_RD |
| Branch (BR/BNE etc., taken or not taken) | f1→c1→e1 | **3T** | FETCH ×1 |
| JSR | f1→c1→s\*→e1→p1→w1 | **7–10T** | FETCH+MEM\_WR |
| RTS | f1→c1→o1→e1 | **5T** | FETCH+MEM\_RD |
| SOB (taken or not taken) | f1→c1→e1 | **3T** | FETCH ×1 |

Verify measured values for each instruction in the corresponding screenshot.

## 4. Category-by-Category Timing Explanation

### 4.1 Single-Operand Register Direct (01–14)

Representative: `CLR R1`

```text
T: -20… -1 | 0  +1 +2 +3  +4
ISN:        |[CLR R1              ]
istate:     | f1  c1  d1  e1  w1
Cycle:      |[FETCH               ]
```

- Only one bus access: the instruction fetch. No MEM\_RD/MEM\_WR occurs.
- `d1` resolves the register number, `e1` performs the ALU operation, `w1` writes back to the register.
- `SXT` produces different results depending on the N flag (compare cases 09 vs 15).

### 4.2 Double-Operand Register-Register (16–22)

Representative: `MOV R0,R1`

```text
T: | 0  +1 +2  +3  +4 +5
   |[MOV R0,R1            ]
   | f1  c1  s1  d1  e1  w1
   |[FETCH                ]
```

- Both `s1` (source) and `d1` (destination) only resolve register numbers — no bus access.
- `CMP` and `BIT` have no w1 (only PSW is updated; registers remain unchanged).

### 4.3 Immediate Instructions (23–26)

Representative: `MOV #5,R1`

```text
T: | 0  +1  +2 +3 +4  +5  +6
   |[MOV #5,R1               ]
   | f1  c1  s1  s4  d1  e1  w1
   |[FETCH][FETCH             ]
      ↑opcode  ↑immediate
```

- Two-word instruction, so FETCH appears twice consecutively.
- At `s4`, the word pointed to by PC (the immediate value) is read and `PC ← PC + 2` is applied.
- The ISN row during the pre-trigger period shows the disassembly as `MOV #1200,R1`.

### 4.4 Memory Indirect Read (27)

Representative: `MOV (R1),R2`

```text
T: | 0  +1  +2 +3    +4 +5  +6
   |[MOV (R1),R2              ]
   | f1  c1  s1  s4   d1  e1  w1
   |[FETCH    ][MEM_RD        ]
```

- `s4` adds a MEM\_RD bus cycle to read M[R1].
- Setting the M1 probe to `mem_probe=0o1200` causes the M1 row to display RAM contents.

### 4.5 Memory Indirect Write (28)

Representative: `MOV R2,(R1)`

```text
T: | 0  +1  +2 +3    +4 +5  +6
   | f1  c1  s1  d1   d4  e1  w1
   |[FETCH    ][    MEM_WR     ]
                      ↑ WR=1
```

- A MEM\_WR cycle occurs at `d4`. `bus_wr=1` goes High.
- The written value (the contents of source R2) appears on the `Data` bus.

### 4.6 Auto-Increment / Auto-Decrement (29–30)

Representative: `MOV (R1)+,R2`

```text
T: | 0  +1  +2  +3 +4    +5 +6  +7
   | f1  c1  s1  s2  s4   d1  e1  w1
   |[FETCH         ][MEM_RD         ]
```

- At `s2`, the post-operation (`R1 ← R1 + 2`) is performed — the register is updated before the bus read.
- For `MOV -(R1),R2`, the pre-decrement `R1 ← R1 - 2` occurs at `s1`, then the read happens at `s4`.

### 4.7 Indexed (31)

Representative: `MOV 2(R1),R2`

```text
T: | 0  +1  +2  +3   +4    +5 +6  +7
   | f1  c1  s1  s2   s4    d1  e1  w1
   |[FETCH  ][FETCH  ][MEM_RD        ]
      opcode   offset    data
```

- Three bus accesses (opcode fetch, offset word fetch, data read).
- At `s2`, the effective address `= R1 + offset` is computed.

### 4.8 Branch Instructions (33–40)

```text
(taken)     f1→c1→e1  PC→branch target
(not taken) f1→c1→e1  PC→next instruction
```

- **The istate sequence is the same for taken and not taken** (3T). The only difference is the PC value after `e1`.
- w1 does not appear (no PSW update).

### 4.9 Byte Instructions (32, 46–49)

```text
BYTE: __________|‾‾‾‾|_______
                  ↑ High during MEM_RD / MEM_WR cycle
```

#### MOVB to Register Sign-Extends

| Destination | Behavior |
|-------------|----------|
| Register (R0–R7) | Source byte is **sign-extended to 16 bits** and stored in the register |
| Memory | Only the target byte is overwritten (adjacent byte unchanged) |

Example: `M[0o1200] = 0o377` → `MOVB (R1),R2` → `R2 = 0o177777` (correct behavior).

```text
0o377 (byte) = 0b11111111 → bit7=1 → sign-extend → 0o177777 (word)
```

To zero-extend instead, use the idiom `clrb R2` → `bisb (R1),R2`.

## 5. Reading the Pre-Trigger Period

Tests run with the following loop structure:

```text
. = 01000
1:
  <setup instruction>   ← setup (set R1, etc.)
  <observed instruction> ← trigger at trigger_pc
  br 1b                 ← branch back to loop start
```

Before the trigger fires, a pre-run of `pre_ticks=40` clock ticks (≈ 2 loop iterations) fills the
ring buffer with pre-trigger data. Reading the ISN row from left to right shows the repeating pattern
"setup instruction → observed instruction → BR → setup instruction → …".

```text
T:  -20 … -15 … -8 -7 … -1 | 0 …
          ↑                   ↑
       MOV #1200,R1          observed instruction
      (visible from around T=-15)
```

If the setup instruction is long, increase `pre_ticks` or decrease `zoom` to widen the visible range.

## 6. Frequently Asked Questions

### Q1: Why does PhysAddr appear to be 00 for some periods?

When the bus is inactive, `bus_addr_p` returns to 0. This matches the behavior of a real Unibus
(the master releases the bus). A valid address only appears during a bus cycle.

### Q2: Why is PC 2 greater than the fetch address?

The PDP-11 executes `PC ← PC + 2` simultaneously with fetching the instruction word.
By the time a sample is stored in the ring buffer, PC already points to the next address.
The fetch address is confirmed via `PhysAddr` (`VA == PC - 2`).

### Q3: Is it normal for CLR R1 to take 5T?

Yes. The five states f1→c1→d1→e1→w1 make up one instruction. This is consistent with
the real PDP-11/20 CLR register time of ≈ 1.5 µs (≈ 2 bus cycles).

### Q4: Is it a bug that MOVB (R1),R2 gives the result 177777?

This is by specification. When the destination of MOVB is a register, the byte value is
sign-extended to 16 bits before being stored (see section 4.9).

### Q5: Some samples have a blank ISN row

Samples where istate is not f1 (e.g., c1/d1/e1) retain and display the previous value.
Samples where istate=0 (h1/halt) are blank.

## 7. Worked Example: Complete Reading of MOV (R1),R2

Screenshot: [Gallery → 27-mov-ind-r.png](../../../test/ss/pdp11/index.html)

```text
T axis:  -20…-16  -15…-9  -8…-1  |  0  +1  +2  +3  +4  +5  +6  +7
Cycle: [FETCH ][MEM_RD][FETCH ] | [FETCH      ] [MEM_RD            ]
ISN:         MOV #1200,R1        |  MOV (R1),R2
istate: f1 c1 s1 s4 d1 e1 w1 f1 |  f1 c1 s1  s4     d1 e1  w1
              ↑                  |           ↑
          immediate 1200 fetch   |        M[1200] read
PhysAddr: 1000 1002     1004     |  1006       1200        1010
Data:       12701 1200   5002    |   5002       12345         773
R1:    00→1200                   |                  (unchanged)
R2:                     00       |                        12345
M1(1200):                        |       12345 (throughout)
```

1. **T=-15 to -9**: `MOV #1200,R1` — FETCH×2 (opcode + immediate 1200), R1←1200
2. **T=-8 to -1**: BR return from loop + re-execution of `MOV #1200,R1` in next loop
3. **T=0**: TRIG. `FETCH` at addr=1006 (`MOV (R1),R2` = opcode `005002`)
4. **T=+3 to +4**: `s4` issues `MEM_RD` at addr=1200 (reads M1 value 12345)
5. **T=+5 to +6**: `e1→w1` writes R2←12345
6. **T=+7**: Fetch of next instruction (BR)

## 9. Generation Method

### Run all 61 cases

```bash
bash scripts/_doTimingSSPDP11.sh
```

### Run specific cases only (`-k` option)

```bash
# Single case
bash scripts/_doTimingSSPDP11.sh -k "nop"

# Multiple cases with OR
bash scripts/_doTimingSSPDP11.sh -k "mov-r-r or clr-r or add-r-r"
```

The arguments after `-k` are passed directly to pytest's `-k` filter.

### Prerequisites

- `.venv` created (`python3 -m venv .venv && .venv/bin/pip install -r requirements.txt`)
- `playwright install chromium` has been run
- `examples/09-pdp11/web/sim.wasm` is built with the latest build (`scripts/build-wasm-09.sh`)
- Port 8080 is available
