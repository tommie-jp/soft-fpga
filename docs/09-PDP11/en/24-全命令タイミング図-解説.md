## Legend

### Number Notation

| Notation | Meaning |
|------|------|
| `0o1000` | Octal. The PDP-11 uses octal for all addresses, instruction words, and register values |
| `177777` | Octal with the `0o` prefix omitted (same format as assembler output and timing diagrams) |
| `#n` | Immediate operand (e.g., the `5` in `MOV #5, R1`) |

### T Axis and Trigger

| Notation | Meaning |
|------|------|
| T=0 | Trigger point. The moment the instruction fetch (M1) of the instruction under observation occurs |
| T<0 | Pre-trigger period. Historical waveform before the trigger (shows the preceding instruction) |
| T>0 | Post-trigger period. Waveform after the trigger |
| nT | Execution time of n clocks (e.g., `5T` = 5 clocks) |

### istate — Microsequencer State

| Symbol | Pronunciation | Meaning |
|----------|------|------|
| `f1` | fetch | Instruction fetch. Reads the opcode from the address in PC |
| `c1` | decode | Instruction decode. Interprets the opcode and determines the sequence |
| `s1`~`s4` | source | Source operand calculation (address computation, memory read) |
| `d1`~`d4` | dest | Destination operand calculation |
| `e1` | execute | ALU operation (add, compare, shift, etc.) |
| `w1` | writeback | Writes the result back to the register |
| `p1` | push | Push to stack (saves old Rn in JSR) |
| `o1` | pop | Pop from stack (restores old Rn in RTS) |

### PSW — Program Status Word

| Flag | Meaning |
|--------|------|
| N | Negative — set to 1 when the result is negative (bit15=1) |
| Z | Zero — set to 1 when the result is zero |
| V | oVerflow — set to 1 on signed overflow |
| C | Carry — set to 1 when a carry occurs |

### Addressing Modes

| Notation | Mode number | Operation |
|------|-----------|------|
| `Rn` | 0 | Register direct — uses the value of Rn |
| `(Rn)` | 1 | Register indirect — references M[Rn] |
| `(Rn)+` | 2 | Post-autoincrement — M[Rn], then Rn += 2 |
| `-(Rn)` | 4 | Pre-autodecrement — Rn -= 2, then M[Rn] |
| `X(Rn)` | 6 | Indexed — M[Rn + X] (X is the following word) |
| `#n` | 2(PC) | Immediate — takes the value from the instruction stream (special form of `(PC)+`) |

### Register Aliases

| Name | Meaning |
|------|------|
| SP | Stack Pointer — alias for R6 |
| PC | Program Counter — alias for R7. Used implicitly by branches and JSR/RTS |

### Bus Cycle Terminology

| Term | Meaning |
|------|------|
| FETCH | Bus read of the instruction opcode (M1 cycle) |
| MEM_RD | Data read bus cycle (other than FETCH) |
| MEM_WR | Data write bus cycle |

### Other Notation

| Notation | Meaning |
|------|------|
| `A→B` | Value changes from A to B (e.g., `R1: 177777→0`) |
| `M[addr]` | Memory contents at address `addr` |
| `CLR R1` at `0o1004` | The instruction `CLR R1` placed at address `0o1004` |

## 1. Phase A — No operand (1 case)

### 1.1 Case 00 — NOP

<details><summary><img src="docs/img/timing/00-nop.png" width="360" alt="Timing diagram"></summary>

![Case 00 NOP timing diagram](docs/img/timing/00-nop.png)

</details>

`NOP` is the PDP-11 "do nothing" instruction (opcode `0o000240`).
It is placed alone at address `0o1000`, followed by a self-loop `br 1b`.
The goal is to verify the **3T minimum pattern** `f1→c1→e1` in istate using a wide view at zoom=32.

The observation point is that only one bus access (the instruction fetch) occurs, and no flag update happens at `e1`. PC is incremented by `+2` after the fetch, but no writeback (`w1`) appears. The pre-trigger period (T<0) shows the preceding loop BR, with FETCH cycles appearing alternately.

## 2. Phase B — Single-operand register (9 cases)

### 2.1 Case 01 — CLR R1

<details><summary><img src="docs/img/timing/01-clr-r.png" width="360" alt="Timing diagram"></summary>

![Case 01 CLR R1 timing diagram](docs/img/timing/01-clr-r.png)

</details>

`CLR R1` sets the destination register to 0 and sets PSW to `N=0, Z=1, V=0, C=0`.
In the pre-trigger period, `MOV $177777, R1` (2 words = 4 bytes, addresses `0o1000`~`0o1003`) writes all-ones into R1, then `CLR R1` at `0o1004` is triggered. This initial value guarantees that "R1 definitely starts from a non-zero value."

The observation points are the **5T pattern** `f1→c1→d1→e1→w1` in istate, and the clock at which R1 changes from `177777` to `0` (the `w1` clock). The Z flag in PSW changing to `1` can also be confirmed at `e1`. Bus access is fetch only (no MEM_RD/MEM_WR).

### 2.2 Case 02 — COM R1

<details><summary><img src="docs/img/timing/02-com-r.png" width="360" alt="Timing diagram"></summary>

![Case 02 COM R1 timing diagram](docs/img/timing/02-com-r.png)

</details>

`COM R1` is the bitwise complement instruction (one's complement). `MOV $5555, R1` (octal) sets the initial value, and `COM R1` is executed at `0o1004`. Verify that the bitwise complement of `0o5555` is `0o172222`.

The observation points are istate `f1→c1→d1→e1→w1` (5T) and the ALU complement operation at `e1`. PSW is set to `N=1, Z=0, V=0, C=0` (`0o172222` is negative). The pre-trigger period shows two FETCHes from `MOV #5555,R1`.

### 2.3 Case 03 — INC R1

<details><summary><img src="docs/img/timing/03-inc-r.png" width="360" alt="Timing diagram"></summary>

![Case 03 INC R1 timing diagram](docs/img/timing/03-inc-r.png)

</details>

`INC R1` adds 1. `MOV $177776, R1` sets the overflow boundary value, then `INC R1` is executed at `0o1004`. `0o177776 + 1 = 0o177777` (the boundary of the maximum positive value).

The observation points are the clock at which R1 changes from `177776` to `177777` (`w1`) and the V flag in PSW (`177776` to `177777` is the unsigned maximum, so V=0; if `177777 + 1`, V=1 would occur, but this case has V=0). istate is 5T (`f1→c1→d1→e1→w1`).

### 2.4 Case 04 — DEC R1

<details><summary><img src="docs/img/timing/04-dec-r.png" width="360" alt="Timing diagram"></summary>

![Case 04 DEC R1 timing diagram](docs/img/timing/04-dec-r.png)

</details>

`DEC R1` subtracts 1. `MOV $1, R1` starts from the minimum positive value, and `DEC R1` is executed at `0o1004`. `0o1 - 1 = 0` (the boundary where Z=1 is set).

The observation points are the clock at which R1 changes from `1` to `0` and the rising edge of the Z flag. Decrementing `0o100000` (minimum negative value) causes a V=1 overflow, but this case demonstrates the normal subtraction pattern where V=0. istate is 5T.

### 2.5 Case 05 — NEG R1

<details><summary><img src="docs/img/timing/05-neg-r.png" width="360" alt="Timing diagram"></summary>

![Case 05 NEG R1 timing diagram](docs/img/timing/05-neg-r.png)

</details>

`NEG R1` is the two's complement negation instruction (`R1 ← 0 - R1`). `MOV $1, R1` provides initial value 1, and `NEG R1` is executed at `0o1004`. The result is `0o177777` (= the two's complement representation of -1).

The observation points are the clock at which R1 changes from `1` to `177777`, and the N flag rising to 1 (`0o177777` is negative). It is useful to observe PSW with the PDP-11 specification in mind: NEG of zero leaves zero with C=0, while all other values produce C=1. istate is 5T.

### 2.6 Case 06 — ADC R1 (C=0)

<details><summary><img src="docs/img/timing/06-adc-r.png" width="360" alt="Timing diagram"></summary>

![Case 06 ADC R1 (C=0) timing diagram](docs/img/timing/06-adc-r.png)

</details>

`ADC R1` adds the carry flag to the register. The pre-trigger period sets the initial value with `MOV $777, R1`. Since the preceding instruction does not modify the carry, `ADC R1` executes with C=0 (with C=0, the addition is `R1 + 0 = R1`, unchanged).

The observation point is that "when C=0, ADC is effectively equivalent to NOP" — the value of R1 does not change, and PSW N/Z are simply set based on the value `0o777`. Experimenting by combining with the BCS case is effective for comparing with the C=1 variant. istate is 5T.

### 2.7 Case 07 — SBC R1 (C=0)

<details><summary><img src="docs/img/timing/07-sbc-r.png" width="360" alt="Timing diagram"></summary>

![Case 07 SBC R1 (C=0) timing diagram](docs/img/timing/07-sbc-r.png)

</details>

`SBC R1` subtracts the carry flag from the register. `MOV $777, R1` sets the initial value and it executes with C=0 (with C=0, `R1 - 0 = R1`, unchanged).

The observation point is that, symmetrically to ADC, "if C=0 the result is effectively NOP." PSW becomes N=0, Z=0 based on the value `0o777`. ADC and SBC are instructions used in multi-precision arithmetic via carry chaining; placing the two cases side by side makes the design where the C flag serves as a chain path clear. istate is 5T.

### 2.8 Case 08 — TST R1

<details><summary><img src="docs/img/timing/08-tst-r.png" width="360" alt="Timing diagram"></summary>

![Case 08 TST R1 timing diagram](docs/img/timing/08-tst-r.png)

</details>

`TST R1` is the "test" instruction — it reads R1's value without modifying it, and only updates the N/Z flags in PSW. `MOV $5555, R1` sets `0o5555`, and `TST R1` is executed at `0o1004`.

The observation point is that PSW is updated even though the register does not change. The istate column is `f1→c1→d1→e1` — **4T** — with no `w1`, because the ALU result is not written back. `0o5555` is positive (N=0, Z=0). V=0 and C=0 are forcibly reset (PDP-11 specification).

### 2.9 Case 09 — SXT R1 (N=1)

<details><summary><img src="docs/img/timing/09-sxt-r.png" width="360" alt="Timing diagram"></summary>

![Case 09 SXT R1 (N=1) timing diagram](docs/img/timing/09-sxt-r.png)

</details>

`SXT R1` is the "sign extend" instruction — it propagates the PSW N flag across all 16 bits: if N=1, `R1 ← 0o177777` (all ones); if N=0, `R1 ← 0`. `MOV $200, R1` writes a value with a zero upper byte, and then `SXT R1` is executed at `0o1004` with N=1 in PSW (note that `0o200` is positive so MOV itself sets N=0 — in practice, the N flag state is taken from the last iteration of the pre-trigger loop).

> **Note**: The N flag immediately before `SXT` executes depends on the PSW set by the last `MOV $200, R1` in the pre-trigger loop. `0o200` = 128 (decimal) is positive, so N=0, which may produce the same result as Phase C's `sxt-r-n0` (case 15). Verify the actual change in R1 from the screenshot.

The observation points are the clock at which R1 changes from `200` to either `177777` or `0`, and the PDP-11-specific behavior of `SXT` — reading the N bit in PSW to determine the execution result.

## 3. Phase C — Shift/Rotate register (6 cases)

### 3.1 Case 10 — ROR R1 (C=0)

<details><summary><img src="docs/img/timing/10-ror-r.png" width="360" alt="Timing diagram"></summary>

![Case 10 ROR R1 (C=0) timing diagram](docs/img/timing/10-ror-r.png)

</details>

`ROR R1` shifts right by 1 bit, bringing in the carry bit at the top. `MOV $1, R1` sets only the LSB to 1, and it executes with C=0. `0o1 >> 1 = 0`, the old bit0 (=1) enters C: `new R1 = 0, new C = 1`.

The observation points are the clock at which C changes from 0 to 1, and the moment R1 changes from `1` to `0`. Both are finalized at the `e1` clock and written back to the register at `w1`. In consecutive RORs, C circulates each time, making carry propagation visible. istate is 5T.

### 3.2 Case 11 — ROL R1 (C=0)

<details><summary><img src="docs/img/timing/11-rol-r.png" width="360" alt="Timing diagram"></summary>

![Case 11 ROL R1 (C=0) timing diagram](docs/img/timing/11-rol-r.png)

</details>

`ROL R1` shifts left by 1 bit, bringing in the carry bit at the bottom. `MOV $100000, R1` (= bit15 only) sets the value, and it executes with C=0. `0o100000 << 1 = 0` (overflows 16-bit width), and the old bit15 enters C. Result: `new R1 = 0, new C = 1, N=0, Z=1`.

The observation points are the N→Z change on overflow and the rising edge of C=1. `0o100000` is the signed minimum value (-32768); you can observe the left-shift boundary behavior where after being pushed to C, R1 becomes 0. istate is 5T.

### 3.3 Case 12 — ASR R1

<details><summary><img src="docs/img/timing/12-asr-r.png" width="360" alt="Timing diagram"></summary>

![Case 12 ASR R1 timing diagram](docs/img/timing/12-asr-r.png)

</details>

`ASR R1` is the arithmetic right shift (preserving the sign bit) instruction. `MOV $100, R1` (`0o100` = 64) sets a positive even number, and ASR is executed. `0o100 >> 1 = 0o40` (= 32). The sign bit (bit15 = 0) is preserved, so the result remains positive.

The observation points are the halving operation where R1 changes from `100` to `40`, and the old bit0 (= 0) entering C (C=0). Using `0o100001` (odd) would produce C=1. This serves as the reference case for comparing arithmetic and logical (ASL) shift symmetry. istate is 5T.

### 3.4 Case 13 — ASL R1

<details><summary><img src="docs/img/timing/13-asl-r.png" width="360" alt="Timing diagram"></summary>

![Case 13 ASL R1 timing diagram](docs/img/timing/13-asl-r.png)

</details>

`ASL R1` is the arithmetic left shift (including the sign bit) instruction. `MOV $1, R1` sets the value, and `0o1 << 1 = 0o2` (= 2). The sign bit does not change and C=0.

The observation points are R1 changing from `1` to `2` (equivalent to multiplying by 2), and the V flag (bit14 XOR bit15 = overflow detection) remaining 0. Using `0o40000` (bit14=1, bit15=0) as the initial value would produce V=1 after the shift. istate is 5T.

### 3.5 Case 14 — SWAB R1

<details><summary><img src="docs/img/timing/14-swab-r.png" width="360" alt="Timing diagram"></summary>

![Case 14 SWAB R1 timing diagram](docs/img/timing/14-swab-r.png)

</details>

`SWAB R1` swaps the high byte and low byte. `MOV $1200, R1` sets the value. `0o1200` has high byte `0o12` and low byte `0o00`. After SWAB, the high byte becomes `0o00` and the low byte becomes `0o12`, giving `R1 = 0o0012`.

The observation points are the byte swap where R1 changes from `1200` to `0012`, and the fact that PSW is set based on the **low byte (the new low byte = the old high byte)**. `0o0012` is positive, so N=0, Z=0. istate is 5T.

### 3.6 Case 15 — SXT R1 (N=0 variant)

<details><summary><img src="docs/img/timing/15-sxt-r-n0.png" width="360" alt="Timing diagram"></summary>

![Case 15 SXT R1 (N=0 variant) timing diagram](docs/img/timing/15-sxt-r-n0.png)

</details>

Same `SXT R1` as case 09, but executed with N=0. After `MOV $177777, R1`, `CLR R2` is executed (PSW: N=0, Z=1), and `SXT R1` at `0o1006` is triggered with N=0. The result is `R1 ← 0` (because N=0).

### 8.3 Design note — The philosophy of `JSR Rx` and its modern evaluation

#### Difference between `JSR PC` and `JSR Rx`

`JSR PC, dst` (using R7=PC) is equivalent to a modern CALL — it pushes the return address onto the stack and jumps. `JSR Rx, dst` (Rx ≠ PC) behaves differently:

```text
1. -(SP) ← Rx          Save old Rx to stack
2. Rx    ← PC          Return address to Rx register
3. PC    ← dst         Jump to subroutine
```

The distinctive feature is that the return address goes into a **general-purpose register** rather than the stack.

#### Use case 1: Hardware coroutines

```asm
; Caller
JSR R3, coro_body     ; R3 = return address A, old R3 on stack

; Return control inside coro_body
JSR R3, caller_cont   ; push R3(=A) to stack, R3 = return address B, PC = A
```

Exchanging resume addresses in a single instruction. Coroutines without an OS are possible.

#### Use case 2: Inline parameter passing (FORTRAN-era convention)

```asm
JSR R5, print_msg
.ascii "Hello\n"      ; embed constants in the code stream
.even
; R5 automatically advances past here and continues execution

print_msg:
    movb (R5)+, R0    ; R5 traverses the parameter list as a pointer
    bne  print_msg
    rts  R5           ; R5 = next address after end of string → return
```

#### Evaluation from a modern architecture perspective

| Aspect | Evaluation |
|------|------|
| Orthogonality / expressiveness | Flexible design allowing any register to be chosen as the link register |
| Coroutines | One instruction in hardware, no OS required |
| **Return Stack Buffer (RSB)** | Only `JSR PC / RTS PC` are RSB-prediction-compatible. `JSR Rx` is treated as an indirect jump, making branch mispredictions more likely |
| **W^X security** | Inline parameters mix code and data, violating modern security policies |
| **Spectre v2 (BTI)** | `RTS Rx` becomes an indirect jump every time, creating a Branch Target Injection attack surface |
| ABI complexity | Multiple calling conventions can coexist. In practice, Unix/C converged on `JSR PC`, effectively making Rx ≠ PC a dead feature |

#### Comparison with RISC-V JAL

RISC-V `JAL rd, dst` shares the same philosophy as PDP-11 `JSR Rx, dst` (storing the return address in an arbitrary GPR). However, RISC-V resolved the RSB problem by specifying in the ABI that "hardware performs return prediction only when `ra` (x1) is used." This can be seen as an improvement on the PDP-11 design, made 50 years later.

`MOV $done, R1` writes the address of the `done:` label into R1, and `JMP (R1)` is executed at `0o1004` (register indirect jump = mode 1).

The observation point is that `JMP`, unlike a branch instruction (3T), goes through an effective address calculation step. istate is `f1→c1→s*→e1`, with the address extracted from R1 at the `s1` clock. No `w1` (no register writeback). PC changes to the value of R1 (the address of `done:`) at the `e1` clock.

### 9.2 Case 44 — SOB taken (R1=2→1)

<details><summary><img src="docs/img/timing/44-sob-taken.png" width="360" alt="Timing diagram"></summary>

![Case 44 SOB taken (R1=2→1) timing diagram](docs/img/timing/44-sob-taken.png)

</details>

`MOV $2, R1` sets R1=2, and `SOB R1, loop` at `0o1004` decrements R1 by 1 and jumps to `loop:` if not zero (`R1: 2→1 ≠ 0` → taken).

The observation point is that the istate sequence `f1→c1→e1` (3T) for `SOB` (Subtract One and Branch) is the same minimum pattern as branch instructions. At `e1`, R1's decrement and the branch decision occur simultaneously. SOB is the most frequent instruction at the end of C loops — equivalent to `do { ... } while (--r1 != 0)`.

#### About `off` in `SOB Rn, off`

`off` is a **backward offset** (6-bit positive integer). The jump target address is calculated as:

```text
Jump target = (address following the SOB instruction) - 2 × off
```

Instruction word bit layout:

```text
15      9  8  6  5       0
┌─────────┬────┬──────────┐
│ 0111 11 │ Rn │  offset  │
└─────────┴────┴──────────┘
 (SOB opc) (3b)   (6b)
```

| Property | Details |
|------|------|
| Direction | **Backward only** (forward jumps not possible) |
| Maximum range | 2 × 63 = 126 bytes backward |
| Usable registers | R0~R5 (SP/PC are not allowed) |

In assembler, writing `SOB R1, loop` with a label causes the offset to be computed automatically. Since a disassembler has no symbols, it displays the numeric form such as `SOB R1, 3` (word count).

### 9.3 Case 45 — SOB not-taken (R1=1→0)

<details><summary><img src="docs/img/timing/45-sob-nt.png" width="360" alt="Timing diagram"></summary>

![Case 45 SOB not-taken (R1=1→0) timing diagram](docs/img/timing/45-sob-nt.png)

</details>

`MOV $1, R1` sets R1=1, and `SOB R1, loop` produces R1=0 (loop terminates). Since `R1: 1→0`, the branch is not taken.

The observation points are that the istate pattern is the same 3T as SOB taken (case 44), with the only difference being PC after `e1` — if not taken, it proceeds to the next instruction (`0o1006`). R1 changing from `1` to `0` is finalized at the `e1` clock (not at `w1`, but at `e1`). Placing case 44 and this case side by side confirms that "execution cost is the same regardless of taken/not-taken."

## 10. Phase J — Byte instructions (4 cases)

### 10.1 Case 46 — MOVB R0, R1 (byte transfer with sign extension)

<details><summary><img src="docs/img/timing/46-movb-r-r.png" width="360" alt="Timing diagram"></summary>

![Case 46 MOVB R0, R1 (byte transfer with sign extension) timing diagram](docs/img/timing/46-movb-r-r.png)

</details>

`MOV $377, R0` sets the low byte of R0 to `0o377` (= `0xFF`), and `MOVB R0, R1` is executed at `0o1004`.

The observation point is that only the **low byte** of R0 is transferred to R1, and **sign extension** is applied. Since R0's low byte = `0o377` (bit7=1), R1 = `0o177777` (expanded to all ones). Although this is a byte instruction, since the destination is a register, bus access is FETCH only (once). istate is 5T (`f1→c1→s1→d1→e1`; analogous to the byte `TST` / `CMP`, though actually `w1` is present and R1 is updated).

> **PDP-11 specific**: `MOVB Rn, Rm` (register-to-register) stores the sign-extended 16-bit value of the source's low byte into all 16 bits of the destination. Same behavior as `MOVB (R1), R2` (memory-to-register).

### 10.2 Case 47 — CLRB R1 (clear low byte)

<details><summary><img src="docs/img/timing/47-clrb-r.png" width="360" alt="Timing diagram"></summary>

![Case 47 CLRB R1 (clear low byte) timing diagram](docs/img/timing/47-clrb-r.png)

</details>

After `MOV $177777, R1` (all ones), `CLRB R1` is executed at `0o1004`. `CLRB` clears **only the low byte** of R1 to 0, leaving the high byte unchanged. Result: `R1 = 0o177400` (the high byte `0o177400` is unchanged).

The observation points are that the high byte is preserved, and PSW is set to N=0, Z=1 based on only the low byte (low byte = 0). Compared to `CLR R1` (case 01), the result differs (full clear vs. low byte only). istate is 5T.

### 10.3 Case 48 — INCB R1 (increment low byte)

<details><summary><img src="docs/img/timing/48-incb-r.png" width="360" alt="Timing diagram"></summary>

![Case 48 INCB R1 (increment low byte) timing diagram](docs/img/timing/48-incb-r.png)

</details>

After `CLR R1`, `INCB R1` is executed at `0o1002` (R1 = 0 → low byte +1 → R1 = 1). A simple case to confirm the basic behavior of INCB.

The observation point is that only the low byte is incremented by 1 while the high byte remains unchanged (stays at zero). At the byte overflow boundary (`0o377 → 0o000`), a signed overflow (V=1) occurs, but this case demonstrates the normal pattern where V=0. istate is 5T.

### 10.4 Case 49 — CMPB R0, R1 (byte compare, Z=1)

<details><summary><img src="docs/img/timing/49-cmpb-r-r.png" width="360" alt="Timing diagram"></summary>

![Case 49 CMPB R0, R1 (byte compare, Z=1) timing diagram](docs/img/timing/49-cmpb-r-r.png)

</details>

After `MOV $5, R0` and `MOV $5, R1`, `CMPB R0, R1` is executed at `0o1010`. The comparison of low bytes (`5 - 5 = 0`) produces Z=1.

The observation point is that `CMPB` compares **only the lower 8 bits** (the upper byte is ignored). istate is the same 5T pattern as `CMP` (case 17) (`f1→c1→s1→d1→e1`, no `w1`). A typical pattern used for comparing array elements of byte data.

## 11. Phase K — Addressing mode showcase (5 cases)

Phase K fixes the `MOV` instruction and systematically compares each addressing mode. The number of bus accesses, number of istate stages, and whether R0 changes can be visually contrasted.

### 11.1 Case 50 — Mode 0: MOV R0, R1 (register direct)

<details><summary><img src="docs/img/timing/50-mode0-reg.png" width="360" alt="Timing diagram"></summary>

![Case 50 Mode 0: MOV R0, R1 (register direct) timing diagram](docs/img/timing/50-mode0-reg.png)

</details>

`MOV $042, R0` sets R0=`0o42`, and `MOV R0, R1` is executed at `0o1004`.

The observation points are **1 bus access** (FETCH only) and the shortest dual-operand 6T pattern. Register direct (Mode 0) is the fastest addressing with no memory access at all. Same structure as Phase D's MOV R0,R1 (case 16), and the baseline case for Phase K.

### 11.2 Case 51 — Mode 1: MOV (R0), R1 (register indirect)

<details><summary><img src="docs/img/timing/51-mode1-ind.png" width="360" alt="Timing diagram"></summary>

![Case 51 Mode 1: MOV (R0), R1 (register indirect) timing diagram](docs/img/timing/51-mode1-ind.png)

</details>

With R0=`0o1200` and M[1200]=`0o123`, `MOV (R0), R1` is executed at `0o1006`.

The observation point is the difference from Mode 0 — a MEM_RD (a green band, not FETCH) is added at the `s4` clock. Bus accesses increase to a total of 2 (FETCH once + MEM_RD once) for 7T. The M1 probe displays the value of M[1200] on the timeline.

### 11.3 Case 52 — Mode 2: MOV (R0)+, R1 (post-autoincrement)

<details><summary><img src="docs/img/timing/52-mode2-autoinc.png" width="360" alt="Timing diagram"></summary>

![Case 52 Mode 2: MOV (R0)+, R1 (post-autoincrement) timing diagram](docs/img/timing/52-mode2-autoinc.png)

</details>

With R0=`0o1200` and M[1200]=`0o456`, `MOV (R0)+, R1` is executed at `0o1006`. After execution, R0: `0o1200`→`0o1202`.

The observation point is the difference from Mode 1 — an `s2` clock is added where R0 is incremented first, then memory is read at `s4`. istate is 8T (1T more than Mode 1). The timing of R0's change at `s2` (before the memory access) is clearly visible in the waveform.

### 11.4 Case 53 — Mode 4: MOV -(R0), R1 (pre-autodecrement)

<details><summary><img src="docs/img/timing/53-mode4-autodec.png" width="360" alt="Timing diagram"></summary>

![Case 53 Mode 4: MOV -(R0), R1 (pre-autodecrement) timing diagram](docs/img/timing/53-mode4-autodec.png)

</details>

With R0=`0o1202` and M[1200]=`0o765`, `MOV -(R0), R1` is executed at `0o1006`. At `s1`, R0: `0o1202`→`0o1200` (decremented first), then M[1200] is read at `s4`.

The observation point is the asymmetry with Mode 2 — increment occurs at `s2`, but decrement occurs at `s1` (pre-decrement is the first step of source address computation). istate is 7T (same number of stages as Mode 1, but with decrement at `s1` instead of `s2`).

### 11.5 Case 54 — Mode 6: MOV 2(R0), R1 (index addressing)

<details><summary><img src="docs/img/timing/54-mode6-idx.png" width="360" alt="Timing diagram"></summary>

![Case 54 Mode 6: MOV 2(R0), R1 (index addressing) timing diagram](docs/img/timing/54-mode6-idx.png)

</details>

With R0=`0o1200`, M[1200]=`0`, and M[1202]=`0o321`, `MOV 2(R0), R1` (a 2-word instruction at `0o1006`~`0o1011`) is executed. Effective address = `R0 + 2 = 0o1202`, and the value `0o321` enters R1.

The observation point is **the most bus accesses at 3** (opcode FETCH → offset `2` FETCH → M[1202] MEM_RD). The offset is FETCHed at `s1` (PC +2), the effective address is computed at `s2`, and data is read at `s4`. istate is 8T. Viewing Modes 0, 4, and 6 together provides an at-a-glance understanding of the cost hierarchy of addressing modes — "as memory references increase, so do bus accesses and istate stages."

## 12. Phase N — EIS instructions (6 cases)

EIS (Extended Instruction Set) instructions were previously handled in software, but it has been confirmed from timestamps that the cpus-pdp11 RTL bundles `mul1616.v` / `div3216.v` / `shift32.v` and implements them fully in hardware. This phase visualizes the **hardware multi-cycle wait** of each instruction in timing diagrams.

zoom=8 is used (1/4 of the 8080 phase). At a 1100px viewport, approximately 137 samples are displayed, and the flat waiting periods of ~16 clocks for MUL and ~32 clocks for DIV fit within the screen.

The signal group is `SIG_EIS = SIG_STD + ['istate', 'r0', 'r1']`. Adding r0/r1 allows direct observation of the moment when products, quotients, and remainders are stored.

---

### 12.1 Case 55 — MUL R1, R0 (16×16 multiply)

<details>
<summary>Timing diagram</summary>

![55-mul-r-r](docs/img/timing/55-mul-r-r.png)

</details>

With R0=`3` and R1=`5`, `mul r1, r0` is executed.

`MUL src, Rn` computes `Rn` × `src` and stores the 32-bit result in `Rn:Rn+1` (when n is even). Since R0 (even) is the target, the product `15=0o17` goes into R0:R1. The lower 16 bits are `R1=0o17` and the upper 16 bits are `R0=0`.

The hardware implementation is `mul1616.v`, a signed 16×16 sequential multiplier (~16 clocks). **Observation point**: `istate` remains fixed at `e1` (execute phase) while r0 and r1 do not change — the flat period. With the assertion of `mul_done`, the product appears in r1 and istate advances.

---

### 12.2 Case 56 — DIV R2, R0 (32÷16 divide)

<details>
<summary>Timing diagram</summary>

![56-div-r-r](docs/img/timing/56-div-r-r.png)

</details>

With R0=`0`, R1=`0o17` (=15), and R2=`3`, `div r2, r0` is executed.

`DIV src, Rn` computes `Rn:Rn+1` ÷ `src` and stores the quotient in `Rn` and the remainder in `Rn+1`. Dividing {R0,R1} = `{0, 0o17}` = 32-bit value 15 by R2=3 gives quotient `R0=5` and remainder `R1=0`.

The hardware implementation is `div3216.v`, a signed 32÷16 sequential divider (~32 clocks). **Observation point**: A longer `e1` flat period than MUL (~twice as long). With the assertion of `div_done`, the quotient 5 appears in R0.

---

### 12.3 Case 57 — ASH #3, R0 (left shift 3)

<details>
<summary>Timing diagram</summary>

![57-ash-pos](docs/img/timing/57-ash-pos.png)

</details>

With R0=`0o100` (=64), `ash $3, r0` is executed.

`ASH cnt, Rn` shifts left if cnt is positive, or arithmetic right shifts (preserving the sign bit) if negative. Interpreted as a 6-bit signed immediate, `3` → left shift 3 → `64 × 8 = 512 = 0o1000`.

The hardware implementation is `shift32.v` (variable-cycle shifter). **Observation point**: A shorter flat period than MUL/DIV. The number of cycles is proportional to the shift amount.

---

### 12.4 Case 58 — ASH #-2, R0 (right shift 2)

<details>
<summary>Timing diagram</summary>

![58-ash-neg](docs/img/timing/58-ash-neg.png)

</details>

With R0=`0o100` (=64), `ash $177776, r0` is executed.

The lower 6 bits of the immediate = `0o76` = 6-bit signed `-2` (arithmetic right shift 2). `64 >> 2 = 16 = 0o20`. An **arithmetic shift** that preserves the sign bit.

**Observation point**: Same `shift32.v` as `ash-pos`, but shifts in the opposite direction based on the sign of cnt. Even with right shifts, the istate flat period is proportional to the shift amount.

---

### 12.5 Case 59 — ASHC #4, R0 (32-bit left shift 4)

<details>
<summary>Timing diagram</summary>

![59-ashc-r](docs/img/timing/59-ashc-r.png)

</details>

With R0=`0` and R1=`1`, `ashc $4, r0` is executed.

`ASHC cnt, Rn` arithmetic-shifts `Rn:Rn+1` as a 32-bit value. {R0,R1} = `{0, 1}` = 32-bit value 1 left-shifted by 4 → 16 = `0o20`. R0=`0`, R1=`0o20`.

**Observation point**: The 32-bit extension of ASH. Observing r0/r1 side by side confirms that 32-bit shifting operates across the register pair.

---

### 12.6 Case 60 — DIV divide-by-zero (V=1 abort)

<details>
<summary>Timing diagram</summary>

![60-div-ovf](docs/img/timing/60-div-ovf.png)

</details>

With R0=`1`, R1=`0`, and R2=`0`, `div r2, r0` is executed.

Divisor R2=0 is a divide-by-zero. `div3216.v` in the RTL asserts the `div_abort` signal and aborts early, setting the V flag (overflow) to `1`.

**Observation point**: Compared to a normal DIV (case 56, ~32 clocks), the `e1` flat period is significantly shorter. Due to the early-exit path in `div_abort`, execution is cut off as soon as the divide-by-zero is detected. The values of r0 and r1 are not modified; only V=1 is set.
