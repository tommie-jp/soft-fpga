# 42. V6 as Assembler Limitations and Pitfalls

This document summarizes the constraints to be aware of when using `/bin/as`
(the Unix V6 PDP-11 assembler) on this disk image directly.
If you compile via `cc`, you will normally not encounter these issues.

---

## 1. Local Numeric Labels (`1:`, `1f`) Are Not Supported

The `as` on this disk image is an older version that does not implement
local numeric labels.

```text
# NG — Memory fault -- Core dumped
1:
    add r0,r1
    sob r0,1b    ← crashes on 1f / 1b references

# OK — use named labels instead
loop:
    add r0,r1
    sob r0,loop
```

---

## 2. `.word label` Inside `.text` Is Not Resolved

Even if you place `.word label` inside the text segment, `as` cannot resolve it on its own.
Regardless of whether the reference is forward or backward, `as` emits a "u NNNN" message and
treats it as a **relocation entry (for `ld`)**.
If you run the resulting `a.out` directly without `ld`, that word will hold an unresolved,
incorrect address.

```asm
; NG — .word label inside .text is not resolved by as
.text
start:
    sys 4
    .word 1
    .word buf     ← unresolved even if buf is in .text
    .word 1
    sys 1
buf:
    .byte 101     ← 'A'
```

**Solution**: Place data in the `.data` segment and use `ld` to resolve cross-segment references.

```asm
; OK — place data in .data and let ld resolve it
.globl start
.text
start:
    sys 4
    .word 1
    .word buf     ← cross-segment ref → resolved by ld
    .word 1
    sys 1
.data
buf: <A>
```

```text
# After generating with as, resolve relocations with ld before executing
as prog.s
mv a.out prog.o
ld prog.o
a.out
```

> Rename the input file as shown above before running `ld`.
> Using `ld a.out` (same name for input and output) is a known V6 `ld` bug
> that truncates the input file.

---

## 3. Only One Cross-Segment Reference Is Reliably Resolved

`ld` handles `.word label` cross-segment references, but
**when a single file contains more than one cross-segment reference,
the second and subsequent ones may be resolved incorrectly**.

| Number of cross-seg refs | Behavior |
|--------------------------|----------|
| 1 | Resolved correctly (confirmed with wr.s) |
| 2 or more | Resolution of the second and beyond may be broken |

If multiple data addresses are needed, **combine them under a single data label**
or redesign to avoid relocation.

---

## 4. `ld` Writes Binary Data to stdout

`ld` writes binary data such as the symbol table to stdout.
This is harmless on a terminal, but when inspecting the output of `a.out`
from a script, be aware that NUL bytes (`\0`) may be mixed in.
`strstr` stops at NUL and cannot detect characters after it; use `memmem` instead.

---

## 5. Recommended Workflow

```text
# 1. C compilation (recommended: let cc handle everything)
cc prog.c
a.out

# 2. Writing assembly directly (following the constraints above)
as prog.s          → a.out (can run directly if ≤1 cross-seg ref)
# or
as prog.s
mv a.out prog.o
ld prog.o          → a.out (ld resolves cross-seg refs)
a.out
```

Forward references in branch instructions (`br`, `bne`, `beq`, etc.) are resolved by `as`
in pass 2, so `ld` is not needed for relative jumps between labels.

---

## 6. Facts Confirmed by ptrace Testing

Results from hands-on testing with `tests/v6-scripts/10-ptrace-probe.v6`:

| Test | Result | Meaning |
|------|--------|---------|
| `sys 4` (write) → 1 character in `.data` | Output correct | as + ld working |
| `sys 2` (fork) → parent writes | Output correct | fork working |
| `sys 32` (ptrace TRACEME) + exec | Does not stop | → see `14-db` §9.1 |
